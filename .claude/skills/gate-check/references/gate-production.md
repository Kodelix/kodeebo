# Gate: Pre-Production → Production


**Required Artifacts:**
- [ ] Vertical slice exists in `prototypes/[product]-vertical-slice/` with a REPORT.md (run `/vertical-slice`) — **recommended, not blocking**; if absent, surface as CONCERNS
- [ ] Vertical slice build runs end to end on the real stack (database → API → web or mobile → deployable bundle), with retained evidence in the slice's `evidence/` directory — **recommended, not blocking**; if absent, surface as CONCERNS
- [ ] Vertical slice has been used unguided in at least 1 documented session (`/usability-report`) with someone from the ICP — **recommended, not blocking**; if absent, surface as CONCERNS
- [ ] First sprint plan exists in `production/sprints/` (`/sprint-plan`)
- [ ] Epics defined in `production/epics/` with at least the Foundation and Core context epics present (`/create-epics`, then `/create-stories [epic-slug]` for each epic)
- [ ] Stories exist for the first sprint, each embedding its `TR-[feature]-NNN` requirement ID, the governing ADR(s), acceptance criteria incl. negative and cross-tenant cases, and a story type (Logic / Integration / Contract / Security / Performance / UI / Config) with the DoD evidence it needs
- [ ] A research note exists for every feature in the first sprint (`docs/research/<feature>.md`, written from primary sources at the pinned versions) — DoD gate 1
- [ ] Every sensitive story in the first sprint has its threat model with SL-THREAT-MODEL recorded
- [ ] QL-STORY-READY recorded for the first sprint's stories (`/story-readiness`, verdict READY)
- [ ] All MVP-tier feature specs from the domain map are complete (at their effective tier)
- [ ] Master architecture document exists at `docs/architecture/architecture.md`
- [ ] At least 3 ADRs covering Foundation-layer decisions exist in `docs/architecture/`
- [ ] All Foundation and Core context ADRs have status `Accepted` (not `Proposed`) — stories cannot be unblocked until their governing ADR is accepted
- [ ] Control manifest exists at `docs/architecture/control-manifest.md` (generated by `/create-control-manifest` from Accepted ADRs)
- [ ] UX specs exist for the app shell and the key screens in `design/ux/`; all key screen UX specs have passed `/ux-review` (verdict APPROVED, or NEEDS REVISION accepted)
- [ ] `PRODUCT.md` and `DESIGN.md` exist at the repository root with DD-DESIGN-SYSTEM recorded
- [ ] CI is green on the default branch: the suites for every layer in scope pass (Section 3 runs them)
- [ ] PR-EPIC and PR-SPRINT recorded (per director-gates.md; skipped by mode is recorded as skipped)

**Quality Checks:**
- [ ] **The core journey delivers its value** — the vertical slice's usability report confirms someone from the ICP completed the central journey of the product and got what the brief promises, not just that the endpoints respond. Explicitly check the slice's report.
- [ ] **The architecture holds up under the slice** — the slice's Architecture Validation rows (tenancy isolation, auth, migrations, observability trace, deploy) are PASS or explicitly accepted; a NOT RUN row stays NOT RUN
- [ ] UX specs cover all user-facing requirements from the MVP-tier specs
- [ ] Interaction pattern library documents the patterns used in the key screens
- [ ] The accessibility target from `design/accessibility-requirements.md` is addressed in all key screen UX specs
- [ ] Sprint plan references real story file paths from `production/epics/` (not just specs — stories must embed the requirement ID and ADR reference)
- [ ] Architecture document has no unresolved open questions in Foundation or Core contexts
- [ ] All ADRs have Stack Compatibility sections stamped with the pinned version, and ADR Dependencies sections (even if all fields are "None")
- [ ] Manual validation confirms specs + architecture + epics are coherent (run `/review-all-specs` and `/architecture-review` if not done recently)
- [ ] **The product's value is delivered** — at least one ICP participant independently described an outcome that matches the brief's value statement for the core journey (without being prompted)
- [ ] `bash .claude/scripts/project-coherence.sh` run: `LICENCE` lines are Blockers (self-hosted/hybrid); `BEHIND`/`FLOATING` are CONCERNS; `SKIPPED` is NOT ASSESSED (Section 3)

**Vertical Slice Validation** (only run these checks if a vertical slice was built):
- [ ] A human has used the core journey through to the outcome without developer guidance
- [ ] The product communicates what to do within the first 2 minutes of the first-run flow
- [ ] No critical blocker bugs (S1 Critical) exist in the slice build, and no cross-tenant data exposure was observed
- [ ] The core journey feels sound to use (this is a subjective check — ask the user)

> **Verdict rules for the vertical slice:**
> - **Slice was built AND any validation item is NO** → verdict is automatically FAIL. A broken
>   or confusing slice should not advance to Production.
> - **Slice was built but its report says NOT ASSESSED** (nobody has used it) → it is not a
>   PROCEED, and its validation items were not checked (they are not NO): the validation
>   block does not run, so the FAIL rule above does not apply. The gate item is NOT
>   ASSESSED, never passed — and a "not yet" to "a human has used it" means the same.
> - **Slice was not built (skipped)** → downgrade to CONCERNS only, not FAIL. Surface the risk
>   clearly: "Advancing without a validated vertical slice increases the risk of late
>   architecture or journey pivots. Recommended before committing full production scope."
>   The user decides.
> - Skipping is a valid solo or time-constrained call. Shipping a broken slice is not.

## Floors at every tier

- A filled `design/product-brief.md` with its build order, and stories under `production/epics/`.
- A research note for each feature before its code (DoD gate 1): for the first features in the build order at `minimal`, for every first-sprint feature at `standard`/`full`.
- At any tier, a built slice (or, at `minimal`, the current build) that fails the validation below is FAIL.

## Workflow tier reductions

The checklist above is the **`full` baseline**. At lower tiers apply the
reduction for the resolved tier; items not named keep their status above.
Reductions only ever *relax* a requirement — `workflow_overrides` is the
only thing that adds one.

- **`full`** — sprint plan + epics + stories + control manifest + UX specs (reviewed) + design system + MVP specs + Accepted Foundation/Core ADRs + QL-STORY-READY + research notes all required; **the vertical slice keeps its status above** — its usability session is recommended, 1 documented session with 3+ better
- **`standard`** — epics + sprint plan + stories + research notes + Accepted Foundation/Core ADRs required; UX specs reviewed + control manifest + design system + QL-STORY-READY record → recommended; **the vertical slice keeps its status above**
- **`minimal`** — the minimal floor only: a filled **`design/product-brief.md`** with its build order, **stories** under `production/epics/` (the brief's build order is the plan, so there is **no sprint plan**), and the **research note** for the first features; everything else **drops** — sprint plan, epics index, usability sessions, MVP specs, the architecture document, both ADR items, control manifest, UX items (key screen specs, `/ux-review`), design system, and the vertical-slice items (the slice, its usability session, and the validation block) — the two current-build checks below replace them.
  **Quality checks at `minimal`:** every check that reads a dropped artifact drops with it — the sprint-plan, architecture, both ADR, spec-coherence, UX and accessibility checks, and the value-delivered check (no spec holds one). Two still apply, to the current build instead of a slice: **the core journey delivers its value** (ask the user, or read a usability note if one exists) and **it runs end to end** — one complete first-run → core action → outcome cycle on the running stack. A "no" to either is FAIL, as a NO on a built slice is at the other tiers; a "not yet" to the first question means nobody has used the build — NOT ASSESSED.

> **The vertical slice keeps its status at `full` and `standard`.** The
> Pre-Production "vertical slice" floor is NOT upgraded to blocking by the tier
> table — the slice artifacts stay *recommended, not blocking* (absent →
> CONCERNS, not FAIL) at `full` and `standard` alike. At `minimal` they drop —
> the minimal route never builds a slice — and the two current-build checks
> replace them. The genuinely-required floor items at this gate are the
> **sprint plan** at `standard` and `full`, and the **brief's build order plus
> stories** at `minimal`. The one hard rule that binds at every tier: if a
> vertical slice *was built* and any of its validation items is NO (at
> `minimal`, if the current build fails either of its two checks), the verdict
> is FAIL regardless of tier — tier reductions relax what must *exist*, never
> what must *work*.

## Director gates at this transition

The PHASE-GATE panel (Section 4b) runs at the width `workflow` sets. Recorded,
not re-spawned: PR-EPIC, QL-STORY-READY (per story), PR-SPRINT, SL-THREAT-MODEL
(per sensitive story), CTO-MANIFEST, DD-DESIGN-SYSTEM; PD-USABILITY on the
slice's usability report (it is skipped by design when nobody has used the
slice — PD-USABILITY records "skipped — no unguided session yet").
