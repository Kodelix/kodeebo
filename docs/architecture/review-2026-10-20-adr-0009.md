## Verdict: FAIL (founder decisions and text fixes)

**2 BLOCKER · 6 MAJOR · 12 MINOR.**

Two findings block acceptance. Both concern the headline rule, "the deploy agent never sees a secret", and the honesty of its caveat:
- **B1:** the ADR never says where the founder's own administrative access to the VPS lives. Every "founder-run host step" needs it. Today it sits in the account the agent shares, so the claim "what holds hard *today* is the VPS side" is not established.
- **B2:** the founder signs a digest of an image that the agent built. Nothing ties that digest to the reviewed commit. This stays true after the account move, and the research note left the question open "before the ADR".

Neither blocker needs a new tool, but both need a founder decision. B1 also needs a source if the founder's route stays the Tailscale SSH feature. Each MAJOR has a text fix; M3, M5 and M6 need a founder or `cto` choice.

**Answers to the five questions in the brief:**

1. **Host enforcement of "the agent never sees a secret".** The VPS mechanism is sound as far as it goes: forced command, `restrict`, `from=`, the wrapper ignoring `SSH_ORIGINAL_COMMAND`, one `""` sudo entry, root-owned paths, `ssh-keygen -Y verify` on a copied manifest, and the replay gate. It matches F307–F311 and F410–F411. It has three gaps:
   - **B1:** the founder's admin path to the VPS;
   - **M1:** how the inbox is filled, and how the agent chooses deploy or rollback;
   - **M2:** the Compose definition, which decides the secret mounts, is neither signed nor declared founder-owned.

   The caveat is consistent wherever it appears (Decision 1, Decision 5, Consequences, FP-AGENT-PRIVILEGED-GROUP) but incomplete (B1, B2).
2. **Founder conditions D1–D6.** All of them appear in the Decision (table below).
3. **Is the VPS OpenSSH version the only acceptance blocker?** No. Besides B1 and B2, the research note lists four more items as due "before the ADR" that are neither closed nor deferred by the founder (M6).
4. **Conflicts with Accepted ADRs and registry stances:**
   - ADR-0007/0008 (and `security-baseline.md`) say "encrypted secret file" (M3);
   - ADR-0001's closed role inventory has no read-only catalogue role (M4);
   - ADR-0001/0004 privileged migrations have no stated Flyway path (M5);
   - ADR-0001 C5 has made `pin_writer` functions privileged since 2026-10-20 (m1);
   - ADR-0006's heap rule (m7).

   No registry stance is contradicted, apart from the ADR-0009 entries that carry these findings.
5. **Alternatives.** Alternatives 1–5 have product-specific rejection reasons. Alternative 6 rejects "because the founder decided". Five options the note weighed are missing (m10).

## Findings

### BLOCKER

**B1 — The founder's own administrative route to the VPS is not part of the design, so "the VPS side holds hard today" is not established.**
- **Where:**
  - ADR-0009:110 says that what holds hard today is the VPS side (forced command, sudo entry, signature and replay checks).
  - :114 says a second, founder-only key carries "a different fixed command".
  - :116, :168, :250 and the Migration Plan (steps 5–6) need founder-run host steps. These steps change the deploy script, `allowed_signers`, gate state and secret files, and run privileged migrations as the bootstrap superuser.
  - ADR-0001:116 and TI M49 (tenant-isolation.md:358) say the founder reaches the host "over SSH through Tailscale" / "over Tailscale SSH from the founder's machine", and logs in with peer authentication inside the PostgreSQL container. TI A13 (:70) calls the founder machine "the only route to the server (Tailscale SSH)".
- **Why it matters:** none of those host steps can run through a fixed-command key, so a third credential exists: an interactive admin login, which ADR-0009 never mentions. Today it lives in the account the agent runs as (F402). An unlocked ssh-agent signs for any same-user process with no prompt (F412). A root-equivalent agent therefore has the same shell on the VPS that the founder has. With that shell it can rewrite the wrapper, `allowed_signers` or the gate state, or read the secret files. The forced command, the sudo entry and the signature are then not a boundary.
- **Tailscale SSH:** if "Tailscale SSH" means the Tailscale SSH *feature* rather than OpenSSH over the tailnet, it does not go through `authorized_keys` at all. Its access rules are tailnet policy, so neither `restrict` nor `from=` applies. Whether it tells the agent's future OS account apart from the founder's on the same node is not sourced anywhere in the repo, so the D5 account move may not close it. NOT SOURCEABLE here; it needs `/research` if that route stays.
- **Fix (founder decision; `cto`, `infra-engineer`):**
  - Add a Decision 2 bullet "Founder admin access", with:
    - the transport (OpenSSH over the tailnet; Tailscale SSH off for the VPS, or kept only with a sourced statement of how it is restricted);
    - custody of the founder's admin key: like the signing key, on the encrypted USB or a FIDO2 `ed25519-sk` key with touch, never loaded in an ssh-agent while an agent session runs, used from the clean-context ceremony login;
    - the founder deploy key held the same way. Otherwise "every record says `agent` or `founder` without trusting the client" (:114) does not hold before the move either.
  - Correct :110 to "hard today only if the founder's admin and deploy credentials are out of the agent's reach as stated in § 2".
  - Add the admin path to the trust-boundary line (:211) and to Validation, for example "with the agent session's environment, no SSH login to the VPS other than the forced command succeeds".
  - Amend TI A13/M49 wording with the threat-model amendments.

**B2 — The signature does not bind the image to reviewed code. The rule still rests on the agent after the account move.**
- **Where:**
  - ADR-0009:108 says "The host enforces it".
  - The Summary (:38) and Consequences (:330) say the VPS "refuses any release the founder did not sign".
  - § 3 step 1 (:123): the image is built "on the founder's machine (CI)", which the agent runs.
  - The Risks row at :356 rates "the founder signs an image built from unreviewed code" Low, and says "rebuild-and-compare is open".
- **Research:**
  - Part 4 § 5 item 4 (research:758) says the signature "cannot show that the agent-built image matches the reviewed source". The founder should either rebuild and compare digests in the ceremony context, or accept the residual risk in the ADR.
  - Part 4 OQ 6 (:800) and the consolidated § 9 row (:398) leave this open for `cto`/`security-lead`, due "before the ADR".
  - Part 3 § 5 item 1 (:655) is the same point: the guarantee holds only if a human who is not the agent has reviewed and signed the release.
- **Why it matters:** D5 moves the agent to its own account, but CI still runs as the agent. The agent produces the tarball whose digest the founder signs. So an agent that adds exfiltration code at build time, not in the reviewed commit, ships it under a valid signature. That code then runs with the server keys or `deploy_rt` mounted. The caveat "procedural until the account move" (:110, :172, :339) is therefore too narrow. After the move the rule is still only as hard as the build step.
- **Fix (founder decision):** pick one and state it in Decision 1, § 3 step 2, § 4c, Risks and the TI R-4 restatement:
  - (a) the ceremony rebuilds the image from the reviewed commit outside the agent's reach and compares digests (reproducibility NOT SOURCEABLE, F420: a spike first);
  - (b) the founder builds the release image in the clean-context ceremony session, so the shipped artifact never comes from the agent;
  - (c) accept by name: "until (a) or (b), the rule depends on the founder's review of the commit and on the agent having built the image from it; it is procedural in the build step even after the account move", with an acceptor and a review trigger.

  Re-rate the :356 row to match the choice.

### MAJOR

**M1 — How the three inbox files get to the VPS, and how the agent picks deploy or rollback, is not stated.**
- **Where:**
  - ADR-0009:114: the only agent key is `command=…,restrict` and ignores `SSH_ORIGINAL_COMMAND`.
  - :117 and :216–219: "The agent may only place three files in an inbox".
  - :125: "The agent transfers the tarball, manifest and signature … and triggers the forced command".
  - :133, :219 and IC-DEPLOY-ENTRY: "a second fixed command runs the no-argument rollback script", also on "agent key".
- **The gaps:**
  - The research's own reading of F309 is that a forced command that ignores the client command "takes no input". The ADR names no channel that writes the inbox.
  - With one key there is no way to choose rollback without reading `SSH_ORIGINAL_COMMAND`, which the ADR forbids.
  - Whatever the channel, the inbox is agent-written input to a root script. F411 copies only the manifest. Step 4 (:126) hashes the tarball and then `docker load`s it, which leaves a swap window if the tarball is read in place.
  - Nothing serialises two concurrent invocations, so two runs could both pass the replay gate on the same state.
- **Fix (`cto`, `infra-engineer`):**
  - Choose the input channel and state it in § 2, Key Interfaces and IC-DEPLOY-ENTRY. Either:
    - a separate upload key bound to `internal-sftp`, chrooted to a root-owned directory that holds only the agent-writable inbox, plus the deploy key and a third key for rollback; or
    - the deploy wrapper reads a size-bounded, fixed-format stream of the three files from stdin, with no archive extracted as root.
  - The script copies every input into a root-owned staging directory: regular files only, no symlinks, size caps. It hashes, verifies and `docker load`s that copy, and holds an exclusive lock for the whole run.
  - Add S33 cases and Validation rows: symlinked input refused; tarball swapped after the check is not loaded; concurrent run refused.

**M2 — The Compose definition and the fingerprint values' route into the backend are not covered by the signature or the host rules.**
- **Where:**
  - :131 records a "compose revision", but the manifest fields (:220–229) carry no Compose hash.
  - :250 lists what is root-owned and founder-changed (scripts, wrapper, `allowed_signers`, gate state), and the Compose file is not among them.
  - :128 passes the expected fingerprints "from the verified manifest" without saying how.
- **Why it matters:** the Compose file decides which container mounts which secret file, under which `user:`, on which network, and with which environment. If the pipeline can change it, the agent can mount the backend's keys into another service. That breaks § 3a without touching the signed image. The same applies to the nginx configuration.
- **Fix:** either:
  - the Compose and nginx files are root-owned on the host and changed only by a founder-run step (add them to :250 and to FP-DEPLOY-ENTRY-ARGUMENTS); or
  - they travel with the release: `compose_sha256` (and `nginx_conf_sha256`) are added to the signed manifest, and the files are placed and verified like the tarball.

  State that the script writes the expected fingerprints to a root-owned read-only file mounted into the backend. They must never be an environment value the pipeline sets, nor agent-writable.

**M3 — The server secret files are plain 0400 host files, but the Accepted ADRs and the baseline call them encrypted.**
- **Where:**
  - ADR-0007:191 and :543: the pepper lives in "the encrypted server secret file".
  - ADR-0008:341 and :368: the master key is in "the encrypted server secret file"; the 13.3.1/13.3.3 deviations are accepted "while they sit in the encrypted secret file".
  - `security-baseline.md` line 43: "At-rest encryption for secrets … (envelope encryption, keys outside the DB)".
  - ADR-0009 Current State (:79) repeats "an encrypted secret file". Decision 3a (:137–140) then specifies only owner and mode.
  - Research part 3 § 5 item 3 (2A', research:657) recommends against encrypted-at-rest tooling now, because it needs a decryption key on the host.
- **Why it matters:** acceptance would silently change what two Accepted ADRs, and their accepted deviations, describe.
- **Fix (founder):** state the at-rest form in 3a. Either:
  - (a) "a plain file; at-rest encryption comes only from the KMS envelope at the first paying customer", with dated amendment notes on ADR-0007 § 2 and ADR-0008 item 10, the 13.3.1 deviation re-stated, a recorded deviation from baseline line 43, and Alternative "2B encrypted at rest" added (m10); or
  - (b) design the encryption and the location of its key.

  Whether the VPS disk or volume is encrypted is NOT SOURCEABLE in the repo; do not claim it.

**M4 — The post-deploy catalogue check runs as a role that ADR-0001's closed inventory does not have.**
- **Where:**
  - ADR-0009:130: the check is "run by the root script with a read-only role".
  - ADR-0001 § 1b (:110): the inventory is closed; "a new role needs an ADR amendment", and C4 fails on any unlisted role.
  - TI M50 (:359) also asks for the check "on a schedule".
- **Why no existing role fits:** `deploy_rt` cannot be used, because B4 makes every `deploy_rt` session `migrator`, the owner of every table (F519). That is not read-only.
- **Gaps:** the role's credential is a further secret with no owner or consuming container named. The scheduled check has no runner.
- **Fix:**
  - Name the role (for example `catalogue_rt`: LOGIN, NOSUPERUSER, NOBYPASSRLS, no table grants, reading only the catalogue views the C1–C8 queries need; confirm in a spike that no grant beyond the default catalogue access is required).
  - Add it to the ADR-0001 § 1b amendment note this ADR already carries and to TR-ROLE-INVENTORY (a successor entry). State its secret file and owner UID, and say whether the scheduled M50 check uses it.
  - Add a Validation row: the check role cannot read or write any tenant row.

**M5 — Privileged and bootstrap migrations have no working path through Flyway.**
- **Where:**
  - ADR-0009:127: the founder "runs that migration as the bootstrap superuser on the database host".
  - :149 and Migration Plan 6: a "privileged bootstrap roles script".
  - ADR-0001 Migration Plan 1 (:424): the first migration creates the roles and is privileged.
  - ADR-0004 § 9 (:122) and TI M49: a superuser login is local `peer` only, inside the PostgreSQL container.
- **The gaps:**
  - (1) F121 shows a superuser Flyway run writes `installed_by=postgres`. If the bootstrap is a Flyway version, the history table it creates is owned by the superuser rather than `migrator`. That fails C5 ("`migrator` owns every table"), and `deploy_rt`-as-`migrator` then cannot write it.
  - (2) With peer-only login, the founder cannot run the Flyway job container as superuser unless the socket is shared into it. Applying the file with `psql` writes no history row, so the next `deploy_rt` run retries the version and stops on 42501 every time.
  - (3) Research § 9 (:390) still has "How is a migration marked privileged, and who owns the pre-check?" open. The "committed privileged list" has no stated format or home.
- **Fix (`cto`, `postgres-specialist`):** state that:
  - the bootstrap roles script runs outside Flyway, and the first `deploy_rt` run creates the history table as `migrator`;
  - privileged versions are applied by one named procedure that writes the history row with a matching checksum. For example, the migration job run as the superuser through the PostgreSQL container's socket with `target=<that version>`; extend S52 to prove it;
  - non-role objects in a privileged migration end up owned by `migrator`;
  - the privileged list's file, format and CI check.

  Add a Validation row: a privileged version applied by the procedure is "up to date" for the next `deploy_rt` run, and C5 still passes.

**M6 — The OpenSSH version is not the only open item the research marks "before the ADR".**

Not closed, and not deferred by the founder:
- **(a) Tool licences.** Open for OpenSSH (the chosen signer and verifier) and OSV-Scanner (research § 9 :391; part 4 OQ 11, :805; F420). The note does not establish them for pgjdbc or the CycloneDX Gradle plugin either. Under the founder's "free and open source only" rule, the note confirms only Flyway (F103), Trivy (F501), the Aqua repositories (F509) and ssh-tpm-agent (F418).
- **(b) Claude Code account.** Which Claude Code account type the founder uses, and whether transcript sharing and telemetry are off (research § 9 :395; part 3 OQ :708; F316). ADR-0009 only sets the managed-settings switches.
- **(c) What the founder verifies before signing** (B2; :398, :800).
- **(d) The ceremony and clean-session spikes.** S46 (ceremony script) and S48 (clean-session check), which § 4c relies on (part 4 OQ 9, :803). The Migration Plan names S46 (step 4) but not S48.

**Fix (founder):** list each in the Status block as blocking acceptance, or record the founder's deferral with its trigger, for example "(a) researched before the first signature; (d) before the first signature". Add S48 to Ordering Note (4).

### MINOR

**m1 — The privileged-migration definition leaves out `pin_writer`.** ADR-0009:259 and FP-FLYWAY-ROLE-BY-CALLBACK name only `auth_lookup`, `support_fn` and `audit_writer`. The Accepted 2026-10-20 amendment to ADR-0001 (:225) added `pin_writer` to C5's definer owners and to "privileged migration if created, replaced or re-owned". **Fix:** "a function of any role C5 allows as a definer owner (today `auth_lookup`, `support_fn`, `audit_writer`, `pin_writer`)".

**m2 — The status vocabulary is not one closed list.**
- § 2 (:119) omits `state_missing` (used at :118) and `checksum_mismatch` (Key Interfaces :234).
- No word exists for a tarball hash mismatch, a loaded-digest mismatch or a field-syntax error. Part 4's metrics use `field_syntax` and `namespace_mismatch`.
- IC-DEPLOY-ENTRY has `state_missing` but not `checksum_mismatch`.

**Fix:** one list in Key Interfaces, used by § 2, the registry and `deploy_refused_total{reason}`.

**m3 — Gate-state timing and restore.**
- **When the state is written is not stated** (on verification, or on `ok`). If it is written on verification, a `privileged_migration_pending` or `health_failed` run uses up release N, and the founder must sign again.
- **Restores re-open releases.** Restoring the gate state from an off-host backup older than the last release lets the agent deploy the later, already-signed manifests it still holds. A VPS restore inside ADR-0005's 30-day window has the same effect. ADR-0005 Decision 6 is listed in Depends On but used nowhere in the text.
- **Manifests never expire.** A signed manifest has no expiry (F411; part 4 OQ 8 `not_after`).

**Fix:**
- write the state only on `ok`;
- after any restore, re-initialise it from the highest release in the off-host deploy record;
- decide on a signed `not_after`.

### New findings

**S1 — MINOR — "Network only for dependency fetch" describes no mechanism.** :195 and IC-RELEASE-CEREMONY give the Gradle container network "only for dependency fetch". A container either has network or it does not, unless a proxy or allowlist is set up. **Fix:** say "network on during the build step (nothing secret is reachable from the container)", or name the allowlist. No secret depends on it: the container sees only the checkout and the caches.

**S2 — MINOR — A `record_failed` re-send after `not_after` has passed.** The recovery at :150 re-sends the same manifest N. If the off-host store stays down past `not_after`, that re-send ends `manifest_expired`. **Fix:** state that the founder then signs a fresh manifest N with the same fields and a new `not_after`; the chain still points to N−1.

**S3 — MINOR — IC-DEPLOY-ENTRY's vocabulary list leaves out `record_failed`.** The registry entry's parenthesised list stops at `rolled_back`, and then adds "record_failed is part of the closed vocabulary" as a separate sentence. **Fix:** put the word inside the list, matching Key Interfaces (:263).

**S4 — MINOR — The diagram draws the admin route through the deploy script and leaves out the two phone-held routes.**
- The admin-key edge (:236) enters `SSHD`, which leads only to `SUDO --> DS`, so it reads as if the admin login runs the deploy script.
- The provider and Tailscale admin accounts are not drawn.

**Fix:** a separate `kadmin` node with its own path (sudo, `rollback`, host steps), and a phone-held "provider / Tailscale" node with a dashed edge to the VPS.
