## 1. Question

Kodeebo is a hosted, offline-first point of sale for small owner-run PlayStation/cyber lounges and cafés in Egypt (5–20 stations, a café counter, one Windows 10/11 cashier device per branch in Tier 1, a hosted multi-tenant backend as source of truth; the counter must keep selling offline). Before the Tier 1 scope is fixed and before the sync numbering ADR (sync-note OQ5), the founder needs to know, from ETA's own sources: which businesses the e-receipt (B2C) and e-invoice (B2B) rules oblige and from when (thresholds, phases); whether the POS software or its vendor must be registered or certified; the technical integration (API, device/POS registration, signing, QR code, receipt fields); offline rules (how long a POS may issue offline, upload deadlines); receipt numbering (gap-free? per device or branch? voided and rejected receipts); and data retention. Decisions informed: Tier 1 scope (brief risk 7), receipt numbering (sync-note OQ5), where the ETA integration lives, e-invoice handling and retention. Decision owners: the founder (scope, with counsel), `cto` (ADRs).

## 5. Decision

### 5.1 Recorded decisions (founder, 2026-10-16)

Every decision below rests partly on legal readings that **need counsel**; the four load-bearing gaps in § 9.1 can reopen them. Verdict of this run: **BLOCKED** (load-bearing NOT SOURCEABLE items confirmed by the founder); Status stays Draft. CTO-STACK-RISK skipped - lean mode.

**D1 — Tier 1 scope. Chosen: ETA-ready now, integration built later, with a trigger (P1 option C).** Tier 1 designs the data model, numbering, immutability (returns, never deletions) and receipt fields so that the ETA e-receipt integration can be added without rework; the integration is the first increment after Tier 1. **Trigger:** if ETA's per-venue inquiry (F124) shows any of the three current venues, or a signed prospect, on an e-receipt mandate list, the integration moves into Tier 1.
**Why:** mandates bind by named list, activity and region, not by size (F108); cafés outside commercial centres are named in Phase 6 with dates already past (F103, F107), so café counters are likely in scope, while PlayStation lounges are not named (F125); one inquiry per venue settles it (F124). **Why not the others:** A would leave a probable legal exposure on the café counter undocumented and could make Kodeebo unsellable to venues already on a list; B commits the largest build before counsel answers whether a software-only Windows POS can be registered (F111–F113, F208); D (accreditation) covers hardware terminal models only (F113) and has no found mandatory basis. **Follow-up:** brief risk 7 rewritten (its "does not force Tier 1" wording is contradicted for cafés); founder runs the inquiry for the three venues (OQ-101).

**D2 — Receipt numbering offline (sync-note OQ5). Chosen: device code + a per-device counter that never skips (P3 option A).** A void or return consumes a number and is a new return document; numbers are never reused or deleted; the ETA UUID and `previousUUID` chain (per POS device, F308, F218) are separate fields.
**Why:** ETA's SDK and FAQ impose no sequence: the receipt's identity is the content-hash UUID, `receiptNumber` must only be unique per branch within a submission (F309), and ETA's FAQ says the system has no requirement on the taxpayer's own serial (F320); the per-device chain already makes each device its own sequence; it needs no server, so the counter never waits; with one device per branch (Tier 1) it is in effect gap-free per branch. **Why not the others:** B (server gap-free branch sequence) stops selling offline for a rule the SDK does not set; C (leased blocks) adds a second source of truth and still has gaps — kept as the **fallback** if counsel reads Article 37 as requiring one namespace per branch; D does not change the printed number. **Condition:** ETA's portal says Article 37 of Law 206/2020 requires a sequential "serial number" without erasures (F321; P4 F404, F415); whether that means per device, per branch or gap-free is the first load-bearing gap (§ 9.1). Whether the counter also resets daily (sync-note N1 "local daily counter") is left to the numbering ADR and to counsel's reading of "numbered by date" (F321). **Follow-up:** sync-note OQ5 row points here; numbering ADR (`cto`).

**D3 — Where the ETA integration lives. Chosen: split — the device issues, the hosted backend submits (P2 option B).** The device issues every receipt offline (number, UUID chain, QR, local validation, print, store); the hosted backend is the single ETA client (per-tenant per-POS credentials in a secret store, token cache, batching ≤ 500 receipts / 1.5 MB, submission, callbacks, reconciliation, code-table refresh). The signing step sits behind a port so it can run on the device or the backend once custody is settled.
**Why:** checkout never waits on ETA (F218, F219, F229); ETA callbacks cannot reach a cashier PC behind NAT (F228); ETA drift is fixed in one hosted place instead of a desktop release (F202, F236); fits the hosted source of truth. **Why not the others:** A spreads POS secrets and e-seal handling across shop PCs and loses callbacks and fleet visibility; C needs Docker on a 4 GB cashier PC, handles one POS, was last released 2023-08 and has unknown licence terms (F226, F227); D has no official source. **Conditions:** PreProd run S20 (auth, submit, signature enforcement, `SN`/`SC` acceptance) and signing custody S23 before the ADR is accepted; the 24-hour window (F316) includes the device-to-server hop.

**D4 — E-invoice (B2B) in Tier 1. Chosen: ask the buyer type at the till (P4 option C), with the founder's condition: no extra tap per sale.** "Final consumer" is the default; the business-buyer option appears only when the cashier opens it (principle 3). A sale marked business buyer gets no e-receipt; the owner is guided to issue the e-invoice on ETA's portal. E-invoices issued by the POS itself (P4 option B) are a Tier 2 candidate.
**Why:** ETA splits B2B and B2C by counterparty and says the e-receipt does not replace the e-invoice (F401, F403); ETA can switch on a setting that rejects business-type e-receipts (F419); no value threshold for invoice-versus-receipt was found (F425), so a full build now would rest on unsourced rules. **Why not the others:** A leaves the mixed-sale conflict unhandled at the till; B first costs a second document family before part-2 questions and the obligation are settled.

**D5 — Retention. Chosen: R3 (P4), with the founder's condition: the archive lives on the hosted server only.** The hosted backend keeps every sale, receipt/invoice payload, ETA submission result, cancelled or returned original and audit trail append-only for at least five years after the tax period (F405, F406; cancelled originals F415), as a per-tenant configurable policy, with an owner export carrying a hash manifest. The cashier device keeps only a bounded recent window it needs offline, because the startup integrity check reads the whole local store (sync spike coverage gaps).
**Why:** the keeping duty sits with the taxpayer (F405, F415) and ETA's own retention is unsourced (F422); a bounded device store keeps the integrity check and startup fast on the reference PC. **Why not the others:** R2 relies on an ETA retention period no source states; R1 alone gives the owner nothing to hand an inspector. **Open for the ADR:** the eviction rule (a record leaves the device only after the server has acknowledged it) and how a return is issued for a sale older than the device window (the return needs the original UUID up to 540 days, F311; or the "return without reference" type) — § 9.1.

**Follow-up records:** ADRs (`cto`): numbering (with the sync ADRs), ETA integration channel and signing, retention and device window. Brief: risk 7 row. Threat model: `docs/architecture/threat-models/eta-e-receipt.md` (`security-lead`).
