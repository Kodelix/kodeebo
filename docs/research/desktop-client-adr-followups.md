## 1. Question

Spike round 1 left two runtimes for the Kodeebo Windows cashier app: **A = Compose Multiplatform Desktop (JVM, jpackage/jlink)** and **B = Electron**. Both passed per-user install, the encrypted store under 100 hard kills, raw printing byte-identical at the sink, and the 3 s counter ceiling after a reboot (desktop-note § 5; `prototypes/desktop-client-spike/README.md`). C (Tauri) is not run (founder, 2026-10-17). Five open questions block the runtime ADR, which the founder decides through `/architecture-decision`:

- **OQ8** — an auto-updater for A (none researched; B's electron-updater is covered in desktop-note F324–F327). Part 1.
- **OQ16** — installer format and scope, uninstall behaviour for the local encrypted data, and local database migration at update, for A and B. Part 1.
- **OQ9** — known security advisories for the exact component versions A and B would ship, including a full read of GHSA-9jxc-qjr9-vjxq. Part 2.
- **OQ11** — the licence of every shipped component and what it says a closed-source distributor must do, stated as written (no legal conclusions; "needs counsel" where it applies). Part 2.
- **OQ6** — how the owner Android app is built (native Kotlin/Compose; Kotlin Multiplatform sharing with A; the owner web dashboard as a PWA or web shell), what each shares with A, B and the web dashboard, and what each would share with a Ktor backend **without deciding OQ7** (that stays with `/setup-stack`). Part 3.

This note recommends; it decides nothing. Out of scope: the runtime choice itself, signing-certificate procurement (desktop-note F301–F311), the sync protocol, Windows 7, the Android cashier (Later), iOS.

## 3. Findings

Merge observations that read across the parts (each rests only on the cited rows):

- **M1 — The GHSA-9jxc question is settled for B; part 1's Q-1P3 is answered by part 2.** electron-builder 26.17.0 does not depend on electron-updater; the app declares it itself, and the spike did not (F203). The advisory affects electron-updater up to 6.3.0-alpha.5 and is fixed in 6.3.0-alpha.6 (F201, F116); every published 6.8.x is outside the range, and OSV returns 0 for 6.8.9 and 6.8.10 (F203). The `v26` dist-tag pointing at 6.8.10 suggests that is the line built alongside electron-builder 26, but no source states the pairing (NOT SOURCEABLE, F203). Part 1's design lesson still applies to any updater, ours included: bind the verified path to the file that runs, and sign the manifest (F116, F202).
- **M2 — A's updater is a build-it item, B's an adopt-it item.** The Compose Gradle plugin and jpackage ship no updater (F111, F112); Velopack has no Java SDK (F103); update4j is archived (F113); Conveyor builds its own MSIX package rather than updating the jpackage MSI, and its shift-aware apply, staging and rollback are weak (F107, F110). For B, electron-updater at ≥ 6.3.0-alpha.6 is available (M1). This moves effort, not feasibility.
- **M3 — Neither runtime is advisory-blocked or licence-blocked on what was read, and neither is cleared.** OSV and GitHub advisory lists show nothing open against the shipped versions (F205, F216, F217, F220). But Chromium 152, Node 24.22.0, the Skia/HarfBuzz/ICU natives in Skiko, WiX and NSIS were not searched (F228), and the operative clauses of the GPL, LGPL and MPL parts were not extracted (F227). Counsel is needed for every notice duty (F213, F207, F221).
- **M4 — Patch cadence differs sharply.** B's Electron 44 line had 11 advisories, all fixed by 44.5.0, and 44.9.0 shipped the day after the spike's 44.8.0 (F217, F218): weeks. A's moving part is the JDK, with quarterly advisories (four CVEs on 2026-08-18) and an October update not yet posted (F223): quarters. Either way the updater is a security control, and ASVS 15.1.1 and 15.2.1 require documented remediation time frames (F226).
- **M5 — Uninstall and the local store.** jpackage's per-user MSI wrote its uninstall entry under HKLM (F101); NSIS keeps app data unless `deleteAppDataOnUninstall` is set (F115); MSIX removes redirected `AppData` writes at uninstall, so a store under `%LOCALAPPDATA%` could be deleted with unsynced sales (F117). Where the store lives and what uninstall may delete is a product rule, not a tool default (Q-1P4).
- **M6 — The owner Android app should not tilt A vs B.** The owner app does not sell, so what it would share with the cashier is small, and the API client comes from the OpenAPI contract in every language (part 3 § 5; desktop-note F423, F427). Option 2 (KMP with A) only pays if A wins, and a shared Kotlin `core` with the server exists only under a Ktor backend (desktop-note F428), which is OQ7 and not decided here.
- **M-E1 (merge-time run) — B packages only its runtime modules.** The spike's `app.asar` holds `koffi`, `better-sqlite3-multiple-ciphers` and `node-addon-api` under `node_modules`, plus the app files; electron-builder left the dev dependencies out. The unpacked native binaries include every platform's prebuilds (darwin, linux, musl, openbsd, win32-arm64, win32-ia32), not only `win32-x64`. Evidence: `docs/research/evidence/desktop-client-adr-followups/merge-b-asar-modules.output.txt` (`npx --no-install @electron/asar list …`, electron-builder 26.17.0, 2026-10-17). This narrows part 2's Q5 (F209) to trimming the other-platform binaries and listing notices for those three modules.
