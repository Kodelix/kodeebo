## 1. Question

Two architecture decisions depend on this note, both decided by the founder with `cto`. **ADR-0010 (core-extraction policy)**: the twelve Layer 1 capabilities of `design/specs/domain-map.md` (tenancy, identity with otp and ratelimit, the authorization mechanism, audit, operator console and support access, licensing, plans/entitlements/subscription, notifications, jobs/outbox, observability, product analytics, storage/backup) are built inside the Kodeebo product behind the ports the future `saas-core-kotlin` will expose and are extracted later by `/core-extract`, never core-first. The ADR must say what makes a module liftable without changing its callers: Gradle module, package names, ABI, Flyway migrations, publication. **ADR-0011 (module structure and architecture tests)**: how the 32 logical bounded contexts map to Gradle modules, which tools enforce P-ONCE, P-CLEAN, P-CORE and P-VERTICAL on every PR from the first backend story, and which Gradle version the build pins. The research ran in five parts: (1) Gradle structure and liftability mechanics; (2) the architecture-test tool, tested against four rules (R1 no context but Notifications imports a mail or push client; R2 `domain` imports no infrastructure and `app` sees only ports; R3 Layer 1 imports nothing from Layer 2 or 3; R4 Layer 2 never imports Layer 3); (3) Flyway migrations owned per module, publication and consumption of a lifted module, advisories; (4) the full stack the founder chose (Gradle graph, jraska, Konsist, ArchUnit, ktlint, detekt) on Kotlin 2.4.21; (5) Gradle 9.8.2 as the pin, with an advisory record for leaving 9.7.0. Founder constraints set during the research (2026-10-20) are recorded in § 5.

## 5. Decision

**Decided by the founder, 2026-10-20** (answers given to the main session during this research; `cto` records them in ADR-0010 and ADR-0011, which stay `Proposed` until accepted).

**D1 — Package root and Maven group: `net.kodelix`** (the founder owns kodelix.net). Layer 1 modules use `net.kodelix.core.<module>`, product contexts `net.kodelix.kodeebo.<context>`, and lifted modules publish under group `net.kodelix.core`. The root is fixed from the first line: renaming later changes every caller (part 1 § 4.3, F113).

**D2 — Module structure (A1, with A-i and A-iii(1)).** One Gradle module per bounded context that has backend code; `domain`, `app` and `adapters` are packages inside each module, not modules; placeholders (Restaurant, Retail) and client-only contexts get no module until built; one `app` composition root; one included `build-logic` with a precompiled convention plugin through `kotlin-dsl` (E1: accepts a second Kotlin toolchain in locks and verification, 2.4.10 at Gradle 9.8.2, F519, F521). `implementation` by default, `api` only for types that appear in a module's public API (F106, F111). Dependency locking for project and buildscript configurations in every module **and** in `build-logic`, all lock files committed, one strict `gradle/verification-metadata.xml` (F115, F119, F521, F522). Re-lock with `assemble testClasses updateKotlinAbi --write-locks`, not the resolve-every-configuration pattern (F115); a dependency change re-locks every dependent (F116). The tenant scope helper and its JDBC carrier stay in the tenancy module (ADR-0002). Type-safe project accessors (incubating, F110) versus string project paths is left to ADR-0011 (§ 9).

**D3 — Liftability (B1).** Each Layer 1 module: its own Gradle module depending only on other Layer 1 modules and third-party libraries (F111); the fixed package root of D1; strict `explicitApi()` (F112); a committed ABI dump (`api/<project>.api`) checked by the Kotlin Gradle plugin's built-in `abiValidation()` with `checkKotlinAbi` in the product, and again in the core after a lift (F113, F327, F523). The built-in validation is experimental (F102) and changed its DSL once without a deprecation cycle (F101); the kotlinx binary-compatibility-validator plugin is the named fallback (maintenance mode, unverified at 2.4.21: F104, S16). **A lift changes build files (settings and dependency notation) plus regenerated lock and verification files, never Kotlin source** (F327, F328, F523).

**D4 — Flyway migrations (M1).** Each module owns `src/main/resources/db/migration/net/kodelix/core/<module>/` (product contexts `.../net/kodelix/kodeebo/<context>/`) from its first migration, and the Flyway location is `classpath:` plus that path, unchanged after a lift (F310, F321, F332). Versions are one plain 4-digit integer per module from 0001 (V1 and V0001 are the same version, F305), never reused or renumbered. Each module has its own history table `flyway_<module>` and its own leaf location, so versions cannot collide across modules (F307, F309, F332); parent-directory locations are forbidden (F308). The migration job holds an explicit module list in Gradle dependency order and runs, per module, `failOnMissingLocations=true`, `baselineOnMigrate=true` with `baselineVersion=0` pinned in code (left at 1 it silently skips V0001, F317), a "resolves at least one migration" guard, `validate` with `ignoreMigrationPatterns=*:pending` (F320), then `migrate`, stopping at the first failure (F319, F332). CI tests cover: second module in a non-empty schema, missing location, drifted duplicate, wrong order. `repair` stays a person-only action (F311). **Per-module history tables are supported by executed evidence only** (F322): S13/S30 are re-run on every Flyway bump (§ 9).

**D5 — Publication (P1).** Lifted modules are published with `maven-publish` under `net.kodelix.core` with a fixed version to a file or private repository (choice open, § 9) and consumed by coordinates through a repository restricted with `content { includeGroup("net.kodelix.core") }`; a developer working on both uses `includeBuild` with unchanged notation (F325, F327, F330). Locking and strict verification stay in the consumer (F329, F330). After a lift or a core bump: lock with verification off for that one run, write the verification metadata, then a strict build, reviewed as a diff (F328).

**D6 — Architecture and lint enforcement, on every PR:**

### 5. Decision

**Chosen**: Recommended - pending user decision. The caller records the final choice; `cto` decides through ADR-0010 and ADR-0011.

**For ADR-0010 migration rule (M1):**
1. Each Layer 1 module owns `src/main/resources/db/migration/net/kodelix/core/<module>/` from the first migration (product modules: `.../net/kodelix/kodeebo/<context>/`). The Flyway location string is `classpath:` + that path, in the product and after a lift (F310, F321, F332).
2. Version = one plain 4-digit integer per module starting at 0001, no dots, no zero-padding variants (V1 and V0001 are the same version, F305); a module's numbers never repeat or get renumbered. Collisions across modules are impossible by construction because each module has its **own** history table `flyway_<module>` and its own leaf location (F307, F309, F332). Parent-directory locations are forbidden (F308).
3. The migration job holds an explicit module list in Gradle dependency order and runs, for each module, `failOnMissingLocations=true`, `baselineOnMigrate=true` with `baselineVersion=0`, a "resolved >= 1 migration" guard, `validate` with `ignoreMigrationPatterns=*:pending`, then `migrate`, stopping at the first failure (F317, F319, F320, F332). A CI test must cover: second module in a non-empty schema, missing location, drifted duplicate, wrong order.
4. A lift moves the directory and the resources unchanged; the ABI dump is unchanged (F327); no history rewrite and no `repair` are needed as long as bytes (modulo line endings, F310) and descriptions are unchanged. Any change of bytes after apply is a checksum mismatch that `validate` stops (F311); `repair` stays a person-only action.
5. Use of per-module tables is **supported only by executed evidence** (F322); ADR-0010 should say so and name the Flyway version at which S13/S30 must be re-run (every Flyway bump).

**For ADR-0010 publication rule (P1):** core modules are published with `maven-publish` under group `net.kodelix.core` and a fixed version to a file or private repository; the product consumes them by coordinates, restricted by `content { includeGroup("net.kodelix.core") }`; a developer working on both uses `includeBuild` with unchanged notation (F325, F327, F330). A lift changes: two `settings` lines, the dependency notation in the module build files, the locks and `verification-metadata.xml` (F328); it does **not** change Kotlin source (F327; confirmed for this probe, caveats in F327). It is therefore "build files and generated lock/metadata files only", not "build files only".

**For ADR-0011:** locking and strict verification both stay in the consumer (F329, F330); keep a core included build's tooling versions identical to the product's (F330 B4); re-lock sequence after a lift or core bump is "lock with verification off, then write metadata, then strict build" (F328), reviewed as a diff.

**Why the others lost:** M2 needs `outOfOrder=true` for every module but the highest block (F306) and a number registry; M3 cannot ship from a core jar without renumbering; M4 is the ADR-0009 fallback only. P2 never records a version; P3 is unpinned. 

**Gradle pin (blocking input for ADR-0011):** 9.7.0 lies in the range of three high advisories fixed in 9.8.1 (F334), while KGP 2.4.21 is documented only up to 9.7.0 (part-1 F106). That is a conflict, not resolved here. **Follow-up record**: ADR-0010 and ADR-0011 (yes, both).

### 5. Decision

**Recommended - pending user decision** (the caller records the final choice):

- **Pin Gradle 9.8.2 with KGP 2.4.21 and JDK 21 (option A, with E1).** Evidence: S10, S11, S12, S31 and the part-4 suite all pass on it with results equal to 9.7.0 (F520-F524) and printed no deprecation or unsupported-version warning (F525); it closes the three high advisories that 9.7.0 is inside (F501-F503) with no OSS patch available for 9.7.x; no advisory is known for 9.8.2 (F515). The founder's dev-machine assumption (F527) means the daemon advisories are live on 9.7.0 today.
- **Why 9.7.0 was left (the record asked for):** three high advisories published 2026-10-07 (GHSA-j5m7-59rp-24f5, GHSA-xwqc-3h47-hg64, GHSA-mvvg-497x-hmj8), 9.0.0 to 9.8.0 affected, fixed in 9.8.1 and later, backports only through a paid subscription, and OSV does not flag the old version (F515).
- **Honest limits:** 9.8.2 is one minor above the Kotlin plugin's documented range; the Kotlin side states nothing about 9.8. The result is executed evidence on a small JVM probe (tier E, never overriding the tier 2 table, F505): re-run the probes when KGP, Gradle or JDK moves, and on the first real backend module. The note's wording for ADR-0011: "Gradle 9.8.2, outside KGP 2.4.21's documented 7.6.3-9.7.0 range, verified by S54/S59 (part 5)".
- **Why the others lose:** B (9.8.1) is not newer or better evidenced than A; C leaves three advisories open without an OSS fix; D adds an unpriced commercial route; E2 is unevaluated work.
- **Record**: ADR-0011 (yes) carries the pin, the range deviation and the advisory record.

### 6. Security Notes

- **Controls (looked up in the official ASVS 5.0.0 text, fetched 2026-10-20 from `OWASP/ASVS` tag v5.0.0, `0x24-V15-Secure-Coding-and-Architecture.md`, tier 1):** 15.1.1 (L1) risk-based deadlines for fixing vulnerable third-party versions; 15.2.1 (L1) no component past its remediation deadline (the Gradle bump is this control applied to the build tool); 15.1.2 (L2) an inventory such as an SBOM from trusted repositories; 15.2.4 (L3) components and indirect dependencies come from the intended repository and are protected against dependency confusion (GHSA-j5m7-59rp-24f5 is that failure; strict repository content filtering and strict verification are the stated mitigations; F522 shows verification fails on a tampered or changed jar); 15.2.5 (L3) isolation around risky parts (ceremony container). MASVS is not relevant.
- **Advisories (searched 2026-10-20 18:53 UTC, GitHub repository list and OSV, F515):** Gradle 9.7.0 is inside the three high advisories; 9.8.1 and 9.8.2: none found; KGP 2.4.21: none. OSV returns nothing even for 9.7.0, so watch the `gradle/gradle` advisory list (open question).
- **Abuse cases:** (1) a failing TLS connection to the first repository makes Gradle fall through to a later, attacker-controlled repository: stopped by strict verification and content filtering; the residual is a verification file regenerated and merged unreviewed (FP-UNLOCKED-GRADLE-BUILD-R2). (2) A lower-privilege local process sends a crafted serialized object to the daemon's loopback port on the developer machine (GHSA-xwqc-3h47-hg64); with the founder's assumption this is live until 9.8.2 or the agent-account move. (3) Winning the worker-to-daemon connection race during a build (GHSA-mvvg-497x-hmj8). (4) A poisoned Gradle dependency cache restored into CI: the cached-jar-changed probe fails the build (F522). (5) The ceremony fetch step is the only step with a network (F501 applies there). (6) Treating `--no-daemon` as a mitigation: Gradle does not say it removes the channels (F502, F503), and the suite and CI runs here used it, so it is not evidence either way.
- **Threat model**: not required for this decision; feeds the build-pipeline amendments of ADR-0009.

### 7. Performance & Caching Notes
