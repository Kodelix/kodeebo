## 1. Question

Which backend language and core track does Kodeebo use — **Go** (`stack.backend: go`, `saas-core-go`) or **Ktor/Kotlin** (`stack.backend: ktor`, `saas-core-kotlin`)? Kodeebo is an offline-first café / PlayStation-lounge POS for Egypt, hosted only on one VPS in Docker Compose (nginx the only public listener, PostgreSQL 18.6 with no published port, administration and deploys over Tailscale through an AI-agent CI with a fixed deploy script). The founder writes almost all code alone; a second engineer works occasionally; both know Kotlin and neither has stated Go experience. One-developer maintenance and the number of languages in the product weigh heavily (user brief). Neither core exists yet. The sync spike's Go server is a prototype and decides nothing.

The desktop runtime is undecided: **A** = Compose Desktop (Kotlin/JVM), **B** = Electron (TypeScript) (`desk-`). Every conclusion is stated for A x Go, A x Ktor, B x Go and B x Ktor where it depends on the runtime. The founder's hypothesis, tested here and not assumed: Kotlin lets the offline cashier and the server share one pricing/billing engine (device and server must compute identical amounts: sync- F325, OQ23; spike S308 waits for this decision).

Decision areas (two per part): runtime footprint per tenant on one VPS; build, image and supply chain; PostgreSQL 18 access under the ADR-0002 tenant-context rule; background jobs and the transactional outbox; OpenTelemetry maturity; Ed25519 and ETA cryptography; billing-engine sharing per desktop option; the Tier 1 library ecosystem; maintenance by one developer; hiring in Egypt.

## 5. Decision

**Chosen: Ktor/Kotlin track (`stack.backend: ktor`, `saas-core-kotlin`) — decided by the founder (user), 2026-10-19,** on the recommendation below. Handed to the `cto` for the backend-track ADR, then `/setup-stack`. Verdict of this note: **COMPLETE WITH GAPS** (every unexecuted item below is an owned open question; the founder confirmed none blocks the decision); Status stays `Draft` because NOT SOURCEABLE items remain.

**VPS facts (founder, 2026-10-19; answers Q2):** 8 GB RAM, 2 vCPU, 240 GB SSD, 1 Gbps unmetered. Builds run on the founder's machine through the AI-agent CI, not on the VPS. Consequence: the JVM's extra 75–115 MB per backend process is small against 8 GB (part 1 § 7 table: about 512 MB default heap in a 2 GB container, about 6 GB left for PostgreSQL, nginx and the Collector), so the first switch condition below does not hold; Gradle build time is a cost on the founder's machine, not on the VPS.

**Recommendation (as presented; recorded unchanged): the Ktor/Kotlin track (`stack.backend: ktor`, `saas-core-kotlin`), for either desktop runtime, with two conditions that would switch it to Go.**

Why, weighing the parts against the user's brief (one developer, few languages weigh heavily):
1. **People and maintenance (part 5).** Ktor adds no language in any combination; Go is new to both people in every Go combination, and A x Go puts three languages and three toolchains in the product (F504, F517). This is the area the brief weighs most.
2. **ETA signing (part 3).** The only executed CAdES-BES path is on the JVM with Bouncy Castle 1.86, a library family already in the licence stack (F306, F307, lic- F212). On Go it is forks and leads until S32 runs (F304, F305).
3. **Telemetry (part 3).** The Java agent covers HTTP, SQL, pool metrics, coroutine context and log correlation with no code (F301); Go needs a pre-1.0 third-party database module and product-written log correlation (F302, F303, F311). Same capability, less code on Ktor — subject to reading or testing the agent's PII defaults (F308).
4. **Code sharing (part 4).** The founder's hypothesis holds only in **A x Ktor** (one Gradle module), and that is not executed. In every other combination the recommended sharing is rules per language plus shared vectors (S-2 + S-3), which is track-neutral and already byte-identical in four languages (F401). So the hypothesis is a reason for Ktor only if the desktop ADR picks A.
5. **Libraries (part 4).** Neither track is blocked on any Tier 1 capability (F402–F425).

What the recommendation costs, stated plainly (parts 1 and 2 recommend Go on their own areas):
- **Footprint:** about 75–115 MB more resident memory per backend process, a 2–4x slower start and a 518 MB image (F114, F116, F117), decisive only on a 1–2 GB VPS (F118).
- **Build and supply chain:** slower Gradle builds; dependency locking and verification metadata must be **mandatory in CI** (opt-in by default, F110); the `gradle: "9.7"` pin must become `9.7.0` or move to 9.8.x (F108, Q7); the ktlint/detekt gap needs a `cto` ADR (F130, F416, F520).
- **Data access:** before the export story, S23 (Exposed → JDBC connection for `CopyManager`) and S22b (evict the connection after a `COPY` error) must pass; until then the EXP-2 export uses a small plain-JDBC carrier (1K-b) that evicts the connection on any `COPY` error; jobs stay in Exposed (ADR-0006 Decision 5; F213, F214).
- **Upgrade churn:** several independent upgrade lines and no published Ktor support window (F519, Q-506).

**Conditions that switch the recommendation to Go:**
- the VPS has **2 GB of memory or less** (Q2), where the JVM's extra 75–115 MB competes with PostgreSQL, nginx and the Collector (F118, part 1 § 7 table) — and S18 confirms it with a realistic service. **Does not hold today:** the VPS has 8 GB (founder, 2026-10-19); re-check only if the VPS shrinks; or
- the desktop runtime is **B** and the founder **wants to learn Go** (Q-503): B x Go and B x Ktor both have two languages, and Go then brings the lower footprint, faster builds, the stability promise and no Kotlin lint gap (F505, F516, F520) — **provided S32 shows a Go CAdES-BES path**, or ETA turns out not to enforce signatures (eta- S20); otherwise ETA signing would need a second runtime (C3).

**A x Go is not recommended** in any case: three languages and three toolchains for one developer, and the billing engine would cross a JVM–Go bridge on a preview API (F412, F517).

**Per-area recommendations carried from the parts** (independent of the track choice unless stated): jobs and outbox — own outbox with a per-tenant sweep (2-a), CP pending-work list (2-d) before tenant counts grow (F208); billing — S-2 + S-3 with vectors in `contracts/` or `tools/`, plus S-1 if A x Ktor (F401, F412); OpenTelemetry — O1 (agent) on Ktor with a PII test, O3 on Go; ETA — C1 (Bouncy Castle on the backend); hiring — do not choose the track on Egyptian hiring data (tier 5 only, F510–F513).

**Load-bearing items behind this recommendation that are not yet executed:** S46 (A x Ktor shared module, no Gradle on the part-4 host); S18 (realistic service footprint per track); S32 (Go CAdES); F308 (agent PII defaults); the VPS size (Q2). None changes the direction for A; S32 can change it for B. Q2 is answered (8 GB), so S18 is no longer needed before the ADR.

**Why not Go, for this product:** Go would be a new language for both people in every combination, puts three languages in A x Go, and has no executed CAdES-BES path for ETA signing (S32 open), while its footprint advantage (about 100 MB per process) is small on an 8 GB VPS and its faster builds run on the founder's machine, not the VPS. **Switch-to-Go conditions stay recorded** (above).

**ADR needed:** yes — the backend-track ADR by `cto` (critical: stack and core track), citing this note; then a jobs/outbox ADR once the track is chosen; the billing-sharing choice goes in that ADR or the sync ADR (sync- OQ23).
