## 1. Question

Three decisions for the deploy and build-tooling ADR, each compared with at least two options, licence and maintenance included, under the constraints: zero tooling budget, free and open source only; solo founder-developer (Kamel Mohamed, Kodelix), a second Kotlin engineer works rarely; hosted only on one VPS (8 GB RAM, 2 vCPU, 240 GB SSD, Docker + nginx; PostgreSQL 18 on the same host, unpublished, reachable only over Tailscale); Ktor/Kotlin backend (ADR-0006) built with Gradle with dependency locking and verification; deploys run by an AI agent in CI on the founder's machine over Tailscale.

1. **Migration tool** (part 1): Flyway (Community) vs Liquibase vs a plain versioned-SQL runner, for forward-only PostgreSQL 18 migrations run as a one-shot job before the new app version starts, logging in as `deploy_rt` and running DDL as `SET ROLE migrator`, with privileged migrations run by the founder as the bootstrap superuser (ADR-0001 Decision 1b).
2. **Image and dependency scanning plus SBOM** (part 2): Trivy vs Grype + Syft vs OSV-Scanner alone (pinned 2.6.0), including recent advisories and supply-chain incidents, offline database use and what runs on the founder's machine vs the server.
3. **Deploy pipeline and agent containment** (part 3): how the AI agent deploys without ever reading a secret (TI R-4, M63, M65; SA M26, M28), container hardening, image integrity, rollback, the start-up key-fingerprint check, and the deploy audit.

The founder's preferences (Flyway, Trivy) are hypotheses tested here, not decisions. The decisions are the user's; `cto` records them in the ADR.

**D3 — Deploy pipeline and containment (turns TI R-4 into an ADR rule).** The agent's SSH key is a forced-command key (`restrict`, `from=` the founder machine's tailnet address) that runs one wrapper which ignores `SSH_ORIGINAL_COMMAND` and calls one sudo entry for one root-owned script with no arguments (F307–F309); no shell, no docker group; the script is updated only by the founder on the host. Before it does anything the script verifies a **founder-signed release manifest** (image digest, migration ids, expected key fingerprints, release number, previous-manifest hash, reviewed git commit id) with **`ssh-keygen -Y verify`** against a namespaced `allowed_signers` line, plus the replay gate (F410, F411); `-Y check-novalidate` never decides. ## 5. Decision

**Recommended - pending user decision.** The caller records the final choice; the deciding record is the deploy and build-tooling ADR.

**Chosen (recommendation)**: Option A, Flyway Community 13.10.3 used as a library (`flyway-core` + `flyway-database-postgresql`) from a small `main()` in the backend build, run as a one-shot container command with the `deploy_rt` credential, with option C (the in-house runner) as the named fallback.

**Why**: it is the only candidate whose behaviour I executed against the ADR-0001 role model on PostgreSQL 18.6: login `deploy_rt` with no grants, `SET ROLE migrator`, history table owned by `migrator`, RESTRICTIVE and permissive policies, FORCE RLS and a `SECURITY DEFINER` function with `search_path` applied cleanly, a privileged statement fails safely and rolls back, a tampered file is caught by checksum (F116-F121). The repo is Apache-2.0 (F103), the jars add 4.76 MB (F116), OSV shows no records (F114), and the founder's preference is consistent with the evidence. It matches the solo-operator constraint: no code of ours to get wrong.

**Conditions (all must hold; each is a test in the migration job's CI)**:
1. Always set `flyway.postgresql.transactional.lock=false`; a CI test applies a `CREATE INDEX CONCURRENTLY` migration (F119).
2. Pin Flyway and the Jackson jars exactly, with Gradle dependency locking and verification metadata (bt-F110), and re-run S11 on every Flyway bump, because `initSql` is deprecated and `afterConnect` did not carry the role in my test (F117, F122). If S14 shows no supported way to set the role, switch to option C rather than rely on a removed setting.
3. The pipeline reads `info` first and stops when the lowest pending version is on the privileged list (F121); the privileged list is a committed file checked by CI against ADR-0001 C5, not a Flyway feature.
4. Record the CI job identity in the job log, because `installed_by` is `migrator` (F117).
5. Development "down": Flyway Community does not run `U` files (F105). Keep dev reversibility as `.down.sql`-style files run by a dev-only script, or reset the dev database; S16 must show that inert `U`/down files do not break `validate` in Community.

**Why not the others**: B (Liquibase) fails "free and open-source only" for the maintained 5.x line by the vendor's own wording (F110), and 4.x is open source but has had no release since 5.0; its role and transaction behaviour were not assessed (F123). D (dbmate) has no checksum, no documented role support and a layout the lint script does not parse (F124, F125). C (in-house) is the better technical fit (lint, privileged mark, audit) but moves every locking and failure-state bug to a solo developer; it wins if S14 fails or if Flyway removes `initSql` without a working replacement. goose, golang-migrate and Atlas were not evaluated (F126).

**What would change this**: S14 or S12 failing; a Flyway release that moves a needed Community feature to a paid tier (check the release notes at each bump); the founder deciding that U-file or dry-run support is required; a Gradle verification problem (S17).

**Follow-up record**: ADR yes (deploy and build-tooling ADR; the tool is an architectural dependency of the deploy path and the privileged-migration runbook). Stack-reference file `docs/stack-reference/migration/` to be created after the decision (none exists now).

## 7. Performance & Caching Notes

- **Expected load**: one run per deploy plus the rare person-run privileged migration; a handful of files per release. Not in the request path. Probe timings: 6-21 ms per trivial migration on a local container (F116-F121); the real cost is the table-level lock and index build time on production-sized tables, which no tool changes.
- **Hot paths**: none for requests. Hot spots are lock queues: a blocked `ALTER` queues all queries behind it (`migration-lint.sh` WARN), so each migration sets `lock_timeout`/`statement_timeout`; `CREATE INDEX CONCURRENTLY` must not run under Flyway's default lock (F119).

- **Caching candidates**: none. Cache decision (gate 5): no cache, reason: a migration run is a write path whose truth is the history table; nothing is read repeatedly; caching would risk applying against stale state.
- **Budgets affected**: none of the request budgets in `docs/architecture/perf-budgets.md` (file not read for this part; confirm); the counter 3 s ceiling is unaffected because migrations run before the new version starts and expand-then-contract keeps the old version working.

## 5. Decision

**Recommended - pending user decision** (the caller records the final choice; `cto` decides in the ADR). Specific to one VPS, Tailscale, an AI agent on the founder's machine, and a solo operator.

1. **Key insight for the ADR rule.** A fixed no-argument script stops the agent from *typing* a command that reads a secret. It does not stop the agent from *shipping code that is then run with the secret mounted*: the agent builds and ships the image, and the migration job receives `deploy_rt`. So "the agent never sees a secret" holds only if the host refuses a release that a human who is not the agent has reviewed and signed. Without that, the guarantee is soft. This is reasoning from F304, F311 and F312, not a sourced claim; it is the main point for `cto` and `security-lead` to confirm.
2. **Containment: 1B + 1A + the signature check of 1D.** The agent's key is a forced-command key (`restrict`, `from=` the founder machine's tailnet address) that runs one wrapper that ignores `SSH_ORIGINAL_COMMAND` and calls one `sudo` entry for one root-owned script with no arguments (F307-F309). No shell, no docker group, no sudo beyond that entry (hard, enforced by the host). The script verifies a founder-made signature over the release manifest before it does anything (hard if the signing key is not usable by the agent; soft if it sits unlocked on the same machine). Updating the deploy script itself is a founder-run action on the host, never done by the pipeline (otherwise the agent could rewrite its own boundary). Rule 1C only if sudo is ruled out.
3. **Secrets: 2A' now.** Root-created files outside the repo, owned by the consuming container's UID with mode 0400 (S30 showed the host owner and mode survive into the container), read only by the root script (for `deploy_rt` into the one-shot migration container) and by the backend container (pepper, verifier master key, TOTP key, throttle-HMAC key). Needs a one-line change to SA M26 ("root-owned 0400") or a stated exception, because a non-root backend cannot read a root-owned 0400 file. Encrypted-at-rest tooling (2B) is not recommended now: it adds a tool and a host-resident decryption key for no gain against root compromise (unsourced reasoning); the KMS envelope already planned at the first paying customer is the real step.
4. **Agent side (soft layer, still worth setting).** Claude Code sandbox on, `allowUnsandboxedCommands: false`, `failIfUnavailable: true`, `denyRead` for credential locations, deny rules for reads of secret paths, delivered as managed settings so project files cannot widen them (F313-F315). These are the agent's configuration: a deny rule is "not a security boundary" (F314), and built-in file tools run outside the sandbox (F315). The host (item 2) is what makes the guarantee hold. Disable feedback/survey transcript sharing and telemetry (F316).
5. **Hardening: 3A baseline** with a bounded `/tmp` tmpfs for the JVM; no rootless/userns now (costs NOT SOURCEABLE). Apply `read_only` and the other flags to the real Ktor app and nginx in their own stories.
6. **Integrity: 4B** (tarball over Tailscale, base images pinned by digest, key-based manifest signature). 4C and 4D lose on the stated constraints (offline founder machine, no registry credential); 4A alone loses because nothing independent checks it.
7. **Rollback.** The deploy script keeps the previous release record (image digest, compose revision, manifest) and starts the new version beside the old one, health-gates it, switches, then stops the old (`.claude/rules/deploy.md`). A second no-argument script (`rollback`) re-activates the recorded previous release. Automatic: only "new version failed its health gate before the switch" (nothing is switched). Manual, founder decides: any rollback after the switch. Migrations are forward-only (F303): rollback restores the previous *application*, never the schema, so every release's migrations must be expand-only so the previous application still works; whether the deploy script can check that is an open question for the migration part.
8. **Start-up fingerprint check (design, unsourced; OWASP has no pattern for it, F323).** For each key the backend computes `HMAC-SHA-256(key, fixed label)` and compares the truncated value with the expected one. The label is a fixed ASCII string per key and per purpose, including the key id, giving domain separation; this is preferred over a bare hash of the key because the same key bytes never produce a value usable elsewhere. (For a uniformly random 256-bit key a bare hash is also not invertible; the HMAC is a design preference, not a sourced requirement.) The expected values live in the founder-signed release manifest, which the root script has verified, so an attacker who can replace the key file but not the founder's signing key cannot also change the record. The host copy of the key file and the record being on the same machine is not a defence; the signature is what makes the record "off-host". Failure behaviour: the backend logs only the key label and `ok|mismatch|missing`, never the computed value, and exits non-zero; `restart: on-failure` with a bounded retry count (not an endless crash loop, T10.7/M3); the health gate fails; the old version keeps running; the script records the failure and alerts. Rotation: the founder generates the new key, computes its fingerprint offline, signs a manifest that carries the new expected value (old and new accepted during the re-wrap window, key id as in ADR-0007), then deploys. A mismatch with no deploy in flight is detected only at the next restart: add the scheduled check (open question).
9. **Audit.** Two keys, two fixed actor tags in `authorized_keys` (`command=` is fixed by the root-owned file, F309), so the record names `agent` or `founder` without trusting the client; attribution is only as hard as the separation of the two private keys (soft on a shared machine). The post-deploy catalogue check (M50) is run by the root script, using a read-only role, and its result is written by the script, not reported by the agent. Off-host record: option 7B, location pending the storage ADR.
10. **Agent-visible output.** The wrapper returns only a fixed status vocabulary and exit code; never raw `docker`/`psql`/application stderr (tenant text can steer the agent, SA T10.3; transcripts are held by the provider, F316).

ADR needed: **yes** (deploy and build-tooling ADR; turns TI R-4 into the rule "the deploy agent never sees a secret", and amends SA M26 on the 0400 owner). Not decided here: nginx pin, Tailscale ACLs, the off-host store.

## 5. Decision

**Recommended - pending user decision** (the user decides; `cto` records it in the deploy and build-tooling ADR). Specific to a solo founder, zero tooling budget, an AI agent on the same workstation.

**0. The finding that shapes everything.** On the machine as observed today (F402) the agent is the founder's own user, in the `docker` and `wheel` groups. A member of `docker` is root-equivalent (F310). Against a root-equivalent agent, **no software-only custody on this machine is a hard boundary** — not a USB (while plugged in), not a separate OS user, not a passphrase. What stays hard is (i) a key that is not present (unplugged USB, offline), and (ii) a key that cannot leave a device and needs a physical touch (K2). So the order is: change what the agent is (case U), then choose custody.

**1. Verification (decision 2): V1, `ssh-keygen -Y verify`**, with `allowed_signers` holding one `namespaces="kodeebo-release-manifest-v1"` line per authorised key (with `valid-before` on a retiring key), plus the replay gate of F411 (verify and parse the same copied bytes; exactly one `release=`; next release number only; previous-manifest hash must equal the last accepted; state written by rename; state initialised by the founder and backed up off-host). Why it wins: already on the founder machine (F401), nothing to download, executed offline with the refusals the design needs (F410, F411), and the same verifier works for a file key now and an sk key later (sk verify untested, S45). V2 loses on size (141 MB each side), four 2026 verification advisories including a high-severity bypass (F408) and an undocumented offline mode (F405); V3 loses because it adds a binary, has no hardware-key path and a stale release (F406, F409); V4 is unverified. **Conditions:** never use `-Y check-novalidate` to decide (F410); the host's OpenSSH version and that `ssh-keygen` exists on the VPS must be confirmed (open question); the manifest must carry the git commit it was built from (see item 4).

**2. Custody now (zero money): K1 hardened, in case U.** (i) Run the agent under a **dedicated OS account with no docker, wheel or sudo** (or remove the founder's account from `docker` for the agent's sessions); this one change is what turns "separate user" from soft to hard, and decides whether K3 is a free hard option (open question 1). (ii) Keep the signing key on an encrypted USB, with the founder's three conditions (a)-(c). (iii) Add three conditions the founder did not name: the **ceremony script and the allowed public-key fingerprint live on the USB** and are run by absolute path with a clean environment (`env -i`), not from the home directory; the ceremony **prints every manifest field and its SHA-256 and asks the founder to type the release number** (S46, not built); and **"no agent session running" is checked, not assumed**: list processes, user units, timers, cron and autostart entries for the agent's account and the founder's, and prefer signing after a reboot or from a text-console login (S48 to define and test). (iv) Never pass the passphrase as an argument, never paste it, and read this machine's swap and core-dump settings before relying on the USB (unread). With these, the USB is hard while unplugged (both cases) and hard while plugged **only if** the agent account cannot reach the ceremony login; in case S it is soft, and the note says so.

**3. Upgrade trigger: K2, two FIDO2 keys, at the first paying customer** (the same trigger as the planned KMS move for the server keys). It removes key theft even from a root-equivalent agent, forces a physical touch per release, and keeps `ssh-keygen -Y verify`. Price NOT SOURCEABLE; sk verification and presence-flag handling must be tested (S45) before it is relied on. K3 in case S, K4, K5 and K6 lose: soft or unproven or paid (section 4). K4 (TPM) is the weakest fit: no user-presence feature documented and no `-Y sign` path (F418).

**4. What the signature does and does not mean.** The signature binds image digest, migration ids, fingerprints and release number to the founder's decision. It cannot show that the agent-built image matches the reviewed source: a signature over a digest the founder cannot inspect only proves a human approved *that artifact*. The manifest should therefore carry the reviewed git commit id, and the founder should either rebuild the image in the ceremony context and compare digests (reproducibility NOT SOURCEABLE, F420) or accept the residual risk in the ADR. This is a question for `cto` and `security-lead` (open question 6), not something custody can fix.

**5. Escrow and recovery.** The VPS trust anchor (`allowed_signers`) is changed only by a founder-run host step, so a lost signing key does not lock the founder out; recovery = enrol a new key there. Whether a second copy of the signing key goes on the existing server-key escrow USB (SA M26, kept apart from Bitwarden) is the user's decision: it simplifies recovery but a stolen escrow then yields signing authority as well as server keys (recommend a separate USB).

**What would change this:** if the agent is moved to a dedicated account and the founder accepts a console login per release, K3 (case U) is a zero-cost hard option and the USB becomes its offline backup; if the VPS has no `ssh-keygen`, V3 (0.27 MB) replaces V1; if S43 shows cosign verifies offline with a key and the founder wants one tool for images and manifests, V2 is reconsidered (only at >= 3.1.3); if S45 shows the verifier ignores the touch flag, K2 is judged on the allowed key set alone; if the founder refuses any ceremony friction, the recommendation falls back to soft custody and the ADR must say "the agent never sees a secret" is **not** hard on this machine.

**ADR needed: yes** (deploy and build-tooling ADR: manifest signing, custody rule, verifier, replay gate). Proposed pin changes: none (no stack reference for these tools; nothing pinned).
