## 1. Question

### Part 1 — device binding, seat moves, N5 bound after a move

Kodeebo licenses and prices each cashier device (founder, 2026-10-17). Seats come only from Kodelix, as a Kodelix-signed seat licence per tenant. The owner enrols devices only within those seats (D1-A, amended). A replacement moves its seat and never consumes a new one, and Kodelix is notified of every activation and seat move. This note informs three founder decisions and the credential ADR:

- (a) How is the licence bound to the device's hardware, software and install: a non-exportable TPM- or DPAPI-held key, a hardware/software fingerprint, or both? This includes false lockouts after hardware changes and Windows updates.
- (b) Does every activation need Kodelix approval, or do seat moves get a yearly allowance set by the founder?
- (c) How does the N5 offline grace bound an old device that keeps selling offline after its seat moved?

The desktop runtime is still open (spike round 1 left Compose Multiplatform Desktop and Electron), so every client-side fact here is runtime-neutral.

**Device-mode term mapping** (`.claude/skills/license-design/references/1-scope-and-inputs.md` § 2). Kodeebo is a hosted product whose cashier device enforces the licence while offline. The self-hosted terms of the studio's licensing standards therefore read as follows in this note:

| Self-hosted term | Kodeebo (device mode) |
|---|---|
| instance, installation ID | cashier device; the `device_id` issued at D1-A enrolment |
| per-instance keypair | non-exportable per-device key (TPM where present, else the OS key store: DPAPI) |
| online activation | D1-A enrolment against the hosted service, within the seats in the Kodelix-signed seat licence |
| offline activation files | not needed: enrolment always runs online (D1-A redeem endpoint) |
| grace after expiry | the N5 offline lease: how long the device sells without reaching the server (G below) |
| revalidation schedule | lease renewal on Kodeebo's own sync connection (sync D2-B) |
| instance move or clone | seat move on replacement (b, c); clone detection (a) |
| update eligibility | not applicable: releases are not sold per version (hosted subscription) |

### Part 2 — Ed25519 verification and signing library per runtime; key custody

Which library should **verify** (and, on the issuer side, **sign**) the Kodelix Ed25519 signatures on the seat licence and the N5 offline lease, in each runtime that touches them, and which behaviours may the licence format and the verifier rely on? Runtimes: backend Go 1.27.2 and backend JVM 21 / Kotlin 2.4.21 (the backend track is unset, so both are covered); desktop candidate A (Compose Multiplatform 1.12.2 on Temurin 21.0.12.1, jlink runtime, same JVM row as the backend); desktop candidate B (Electron 44.8.0 with Node.js 24.22.0); signer: the Kodelix issuer service (Go or Kotlin). The installer verifies no licence; the desktop updater's own Ed25519 signature is covered by `desktop-client-adr-followups.part-1-updater-installer.md` and only the shared-library implication is noted (F224). The device's ECDSA P-256 key is out of scope. Decision owners: `cto` (library per runtime and key custody, by ADR), `security-lead` (custody and ASVS exceptions); `licensing-specialist` consumes the format rules in `/license-design`. This note recommends and decides nothing.

### Part 3 — lease clock across reboots and state restore; TPM 2.0 clock

Kodeebo's offline cashier device sells under an N5 offline lease of G = 7 days (base plan; founder, 2026-10-17). The founder decided that a clock rollback never stops sales mid-shift, never extends the lease, and alerts Kodelix and the owner, and that the lease is counted on the device's monotonic clock plus server contact, never on wall time. The founder's design input is: store the Kodelix-signed server time at each contact, encrypted, and add elapsed monotonic time between contacts. This note informs the founder (decider), with `cto` recording the result in the credential and lease ADR, on how the device accounts lease time across **(1) reboots** and **(2) a restore of an older copy of its state file**, and whether the **TPM 2.0 clock** can anchor the count on PCs that have a TPM. It reconciles the founder input with the one clock already recommended in the sync note (D1-B, D2-B, spikes S301-S306); it does not propose a second clock. It does not decide anything.

| F201 | RFC 8032 section 5.1.7 (Verify): split the 64-byte signature into R (32) and S (32). Decode R as a point and S as an integer with 0 <= S < L; decode the public key A. "If any of the decodings fail (including S being out of range), the signature is invalid." Then compute k = SHA512(R, A, M) and check [8][S]B = [8]R + [8][k]A; the RFC also permits checking the unmultiplied equation [S]B = R + [k]A instead. | [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.txt), fetched 2026-10-17, saved `evidence/licensing-part-2/fetched/rfc8032.txt` (kept on disk, git-ignored: § 9 Part 2 evidence index) | 1 | The RFC leaves the cofactor choice to the implementation, so two conforming verifiers may disagree on some malformed inputs (F202). |
| F202 | RFC 8032 section 8.4: Ed25519 signatures are not malleable thanks to the check that decoded S is smaller than L; without it one could add a multiple of L to S and still verify. Section 8.8: the cofactor multiplication is not needed for security, but the RFC notes that some applications need all implementations to accept exactly the same set of signatures (disagreement allows fingerprinting). The RFC text read does not require rejecting small-order public keys or non-canonical point encodings: NOT SOURCEABLE as a MUST in RFC 8032 (grep of the full text for "small order", "canonical", "ZIP215", "strict" found only the S < L rules and the cofactor discussion). | [RFC 8032 s8.4, s8.8](https://www.rfc-editor.org/rfc/rfc8032.txt) (2026-10-17) | 1 | Consequence for the licence format: do not rely on signature uniqueness or on key validity checks being the same across runtimes. | F222 | **Design consequences drawn from F201-F221 (inference, for `licensing-specialist`; not a sourced claim).** (1) Keep the signature over the exact stored bytes of a framed envelope and verify before any parsing; put in the signed bytes a format version, an algorithm id, a key id and a purpose tag (seat licence, N5 lease, update manifest) so one signed blob cannot be replayed as another (ASVS 9.1.2, 9.2.2, 9.2.3 in F215). ### Part 1 — device binding, seat moves, N5 bound after a move

**Chosen**: **Decided by the founder on 2026-10-17: (a) A3, (b) B3, (c) C1 + C2, as recommended.** The `cto` records the binding in the credential ADR; the values below go into the licence model. Status stays Draft: the flagged items (F106, F107, F113) wait for S32/S11, and parts 2 and 3 of this note are pending.

**Values (founder, 2026-10-17):**
- **Offline lease G = 7 days on the base plan.** This meets the brief's "clearly longer than 5 days". Higher plans get longer leases, set with the plans in `/pricing-strategy`, not now.
- **Seat-move allowance = 2 per device seat per year, per seat and not pooled** across a tenant's seats; a move beyond a seat's allowance needs Kodelix approval (B3). With C1, an unreleased move can overlap by at most 7 days, so the extra device-days stay at most 2 × 7 = 14 per seat per year on the base plan.
- **A lease that ends mid-shift does not wait for the shift to close.** The sync note's expiry rule applies (sync OQ3, tested by SC-25b): the cashier and the owner are warned 24 hours before the lease ends; at expiry, open sessions can still be closed and paid; no new session or sale until the device reaches the server; local data stays readable and exportable, and the backlog is accepted at reconnect.
- **Clock rollback** (replaces the open choice between backward-at-boot policies D2-P1 and D2-P2): a rollback **never stops sales mid-shift** and **never extends the lease**. The lease is counted on the device's monotonic clock and on server contact, never on wall time. A rollback **alerts Kodelix and the owner**.

**Founder design input for the clock (2026-10-17), to be reconciled with sync D1-B and spikes S301-S305 (one clock, not a second design):** the lease runs on server time, never the Windows clock. At each server contact the device stores the server time, signed and encrypted. Between contacts it adds the elapsed time from a monotonic counter. Two gaps are researched in part 3 of this note (or in `/threat-model licensing`):
1. **Reboots.** The monotonic counter restarts at boot (desk-F117), so the device keeps a persisted high-water mark. After a reboot, time never goes below it, and a wall clock earlier than it raises an alert. Time while the device is powered off sells nothing. **Superseded by the founder's powered-off rule R-F, confirmed 2026-10-17:** count powered-off time when the Windows clock moved forward across the power-off, so the lease stays about 7 calendar days; count zero and alert when it moved backward below the high-water mark; plus a **server alert**: at each contact the server compares calendar time since the last contact with lease time used and alerts Kodelix when the gap exceeds a threshold (value set in `/threat-model licensing`). Part 3 § 4.2 (R-F) and § 5 record the evaluation and its limits.
2. **Restore of an older state file.** Check whether the TPM 2.0 clock can anchor time on devices with a TPM; the founder understands it cannot be set back, but this must be sourced, not assumed. Without a TPM, the server detects the rollback at the next contact through repeated sequence numbers (sync SC-12; restore/clone policy sync OQ7: the counter keeps selling, sync is quarantined, the owner chooses the real copy).

- **(a) A3.** The binding is the **non-exportable device key**: a TPM key through the Platform provider where a usable TPM exists, DPAPI-wrapped otherwise. The fingerprint is a **change/clone signal that alerts Kodelix, never a binding and never an automatic lock-out**. The device key is ECDSA P-256, so one verifier covers both tiers: CNG lists no EdDSA (F105), and the Platform provider's support for P-256 rests on lead F106 (flagged). Kodelix's own signatures (seat licence, N5 lease) are not limited by CNG, so their algorithm is part 2's question. The key tier is recorded as claimed, not attested (F101). Every key loss is recovered by D1-A re-enrolment, which counts as a seat move under (b).
- **(b) B3.** Owner approval plus the Kodelix-signed seat count gate first activations. Moves are automatic inside a yearly allowance the founder sets, carried in the signed seat licence. Kodelix is notified of every activation and move as a server event. Kodelix approves any move beyond the allowance or carrying an A3 signal. The seat is locked during a move (ASVS 2.3.4).
- **(c) C1 + C2.** Release first when the old device is reachable (zero overlap). Otherwise accept an overlap bounded by the old device's own lease: at most G per move and at most allowance × G device-days per contract year. Post-move sales are accepted and flagged, never rejected (OQ6). The old device turns `retiring` (upload-only) at its next contact.

**Why**:
- (a) A non-exportable key is the only binding a copied disk does not carry: F102 for TPM keys, and desk-F112 for DPAPI's same-computer rule. Its failure modes are discrete events with a known recovery, re-enrolment (F103, F104, F107). A fingerprint gate would turn Microsoft's own failure mode (F108) and Cryptlex's documented need for loose matching (F110) into lockouts, and the studio rule forbids it. As a signal, the fingerprint still gives Kodelix clone visibility that software IDs alone cannot (F109).
- (b) B3 puts a second party (Kodelix) exactly where ASVS 2.3.5 asks for one: issuing seats, which is the high-value step, and the exceptional moves (F114). It keeps the counter selling in the common case of a dead PC. The vendors documented here cap transfers rather than require human approval per move (F110, F111).
- (c) The overlap is the price of the N5 promise. C2 removes it whenever the old device still works. C1 bounds it with values the founder sets (G and the allowance), and the D2-B lease enforces the bound on the device itself (F116), not by trust.

**Why not the others**:
- A2 and A4 are fingerprint bindings. They lock honest venues out after board, disk or fTPM events (F104, F107, F108, F110). The venue administrator can forge them (by analogy with F101; also F109), and the studio rule marks them BLOCKED.
- A1 alone gives Kodelix no clone or hardware-change visibility.
- A5 excludes venue PCs without a TPM (desk OQ3) and rests on unsourced ECC attestation (F113).

### Part 2 — Ed25519 verification and signing library per runtime; key custody

**Recommended - pending user decision** (the `cto` decides by ADR; nothing here is decided).

**Chosen (recommended)**:
- **Go backend:** G1, the standard library, behind a small port that normalises the outcome, plus the shared conformance vectors (F222).
- **JVM backend and desktop A:** J1, the JDK built-in, with `jdk.crypto.ec` added to the jlink module list and the same normalising port; **J2 (Bouncy Castle 1.86) as the fallback** if the team wants small-order and non-canonical-key rejection inside the library, or if S204 shows J1 cannot ship in the jlink image.
- **Electron (desktop B):** N1 in the main process, **conditional on S206** (the vectors passing inside Electron 44.8.0); otherwise N2 with `zip215: false` pinned in a lockfile.
- **Signer:** the issuer service signs with the same library as its runtime, with the private key in a managed KMS that supports Ed25519 (S1 or S2) if `security-lead` accepts a managed service for ASVS 13.3.3; S4 only with a hardware token that does the signing. Custody provider is not recommended on this evidence: prices, limits, regions and GCP protection levels are unsourced.
- **Format rules** (F222): verify over exact stored bytes before parsing; pinned verifying keys never read from the licence; algorithm id, key id and purpose tag inside the signed bytes; fixed 32-byte keys and 64-byte signatures; fail closed on any exception; payload parsed afterwards with duplicate-name detection on.

**Why**: the standard-library options need no dependency and their weaknesses (small-order and non-canonical keys) are unreachable when verifying keys are pinned and Kodelix-generated. The executed vectors (F219) show every library has edge differences, so the protection is the pinned key set plus the conformance suite, not the choice of library alone. Bouncy Castle is the only tested library that rejects all the key edge cases, which is why it stays as the fallback.

**Why not the others**: G2 (circl) and J3 (Tink) add a dependency without closing the small-order case (circl) or with runtime-dependent behaviour (Tink). N2 is safe only with a non-default option. S3 adds a service to run. Azure Key Vault shows no Ed25519 on the page read.

**ADR needed**: yes (algorithm and library per runtime, key custody, format rules); owner `cto`, with `security-lead` for custody. This note's follow-up record: ADR to be written, none exists yet.

### Part 3 — lease clock across reboots and state restore; TPM 2.0 clock

**Recommended - pending user decision** (the founder decides; `cto` records it). Nothing here is decided.

- **One clock.** Keep sync D1-B / D2-B as the single design and read the founder input as its description: anchor = the signed lease (server `iat`, sequence, `grace_seconds`), encrypted at rest; consumed lease time = monotonic time while running plus the persisted ratchet; wall time is read only to raise alerts. Differences to confirm are in § 4.1.
- **Reboot rule: R-A — researcher's recommendation, not chosen (the founder chose R-F above)** (powered time only; wall earlier or later than the mark alerts, never charges), **with the server flagging calendar span against powered span** at each contact (sync D3-B). Why: it is the founder's rule, needs no wall logic, never locks an honest venue (F317), and a wall-clock edit cannot touch it. The price is that G is 7 days of running time (F324): the founder must accept that a venue open 8 hours a day can go 21 calendar days offline before the lease ends. R-B loses because it charges honest venues for every closed night and reintroduces wall time; R-C is better as an alert threshold than as an enforcer; R-D locks honest venues.
- **Decided (founder, 2026-10-17): R-F, confirmed as recorded in § 4.2 including its limits, plus a server alert.** At each contact the server compares calendar time since the last contact with lease time used and alerts Kodelix when the gap exceeds a threshold; the threshold value is set in `/threat-model licensing`. This covers, after the fact, the case of a clock set back to the mark while the device was off. R-A below is therefore not chosen. Evaluation that led to it: Part 3 **confirms** R-F for honest venues and for forward clock edits (F317, F324, R-B row) and **does not reject** it. It shows one **limit**: R-F alerts only below the high-water mark, so an administrator who sets the RTC back to the mark or just above it while powered off gains the gap silently. Their bound is then R-A's (G = 7 days of running time), and the server sees it only at the next contact by comparing calendar span with consumed lease (sync D3-B). Two consequences for the founder to confirm before R-F becomes the decision: (1) accept that residual, or add a server-side alert when calendar span between contacts exceeds consumed lease by more than a configured margin; (2) accept that, with no cap, a long powered-off closure can use up the lease, so the device sells nothing new until it reaches the server (SC-25b rule). R-F also needs the reboot signal of S301/S302 (F318).
- **Restore anchor: A-1 on every PC** (server detection, already planned), **plus A-4** (cheap ratchets). **A-2 (TPM Clock) only as an optional hardening for PCs that have a TPM, and only after the S301 TPM column proves a standard user can read Clock and shows its behaviour on the venue PC models.** Why: the derivation that a restore gives less time with a TPM anchor (F323) is sound on the sourced semantics, but it rests on an unverified permission (F311), on a spec revision two generations old (F301) and on TPM behaviour that differs between discrete and firmware TPMs and is unmeasured (F322). The TPM clock cannot be verified by the server (F307, F308), cannot stop an administrator, and excludes sleep (F315), so it cannot be the meter. A-3 stays a research candidate under OQ27.
- **If the founder wants the TPM path later,** the rule that keeps "never extends the lease" is: use the larger of the software consumed counter and the TPM-derived elapsed time only when they diverge by more than a configured tolerance (the tolerance must cover the 15 percent floor of F316), alert on every divergence, and treat a TPM that becomes unreadable as an alert with the software counter continuing. This is a proposal, not a sourced rule.

ADR needed: **yes**, folded into the N5 lease ADR (sync 5.1.4) and the credential ADR (`cto`). Brief risk 8's pass signal needs rewording (§ 4.1 row 3).

Those remain open.
- **Abuse cases**:
  1. *Forged licence with a substituted key.* If the verifier took its key from the licence, an attacker supplies a small-order key and the matching trivial signature; Go, circl and the JDK accept it for any message (F219). Counter: pinned keys only (ASVS 9.1.3).
  2. *Malleated signature as a "new" licence.* S + L is rejected by every library tested (F219); the JDK reports it by exception. Counter: fail closed; do not use the signature bytes as a unique id.
  3. *Verifier differential.* A non-canonical key or R accepted by one runtime and refused by another lets a licence pass on the backend and fail on the device (or the reverse). Counter: the issuer emits only canonical signatures; the shared vectors run in CI (F222).
  4. *Fail-open on exception.* The JDK and BC throw on malformed input and Go panics on a 31-byte key; a caller that catches broadly and continues grants the licence. Counter: one wrapper that returns "invalid" for every error.
  5. *Cross-purpose replay.* A seat licence signed by the same key as an N5 lease, or an update manifest signed by the licence key, is replayed in the wrong place. Counter: purpose tag in the signed bytes (9.2.2) and separate key per purpose (followups Q-1P8, F224).
  6. *Parser differential after verification.* Duplicate JSON members are accepted by default in Jackson (F220); a licence the issuer built one way could be read differently by another consumer. Counter: strict duplicate detection, plus a size cap before parsing.
  7. *Key compromise on an offline device.* A leaked signing key cannot be revoked on a device that never reaches the server; rotation needs a key-id list shipped with an app update and a runbook (`docs/runbooks/`, per `security-baseline.md`). Counter: key ids, short-lived leases, rotation runbook.
- **Threat model**: required: `docs/architecture/threat-models/licensing.md` via `/threat-model licensing`; not written yet (part 1 § 6).
- **Legal**: nothing in this note interprets law. Whether a managed KMS outside Egypt is acceptable for signing keys (PDPL, data residency) is **needs counsel**; no primary text was read.

  7. Honest Windows backward reset (F317): must not lock or penalize; alert only.
  8. Replay of an older signed lease: rejected by the highest-sequence rule (F319).
