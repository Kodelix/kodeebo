## 1. Question

**Where, and under what controls, should the private key that signs Kodeebo's Ed25519 licences live?** The signatures cover the seat licence per tenant and the N5 offline lease (Part 2), verified offline on cashier devices by pinned public keys (ASVS 9.1.3, F215). The founder's input of 2026-10-17 (not decided; the threat model confirms or rejects it) is a two-level hierarchy: an offline root key (hardware token or air-gapped machine, plus a second backup elsewhere) that signs short-lived issuing keys every few months; the device trusts only the root public key; the issuing key sits in a non-exportable cloud KMS/HSM and signs the daily licences; a stolen issuing key is revoked and replaced without updating any device; two-person approval for production licences; separate keys for licences, updates and the ETA certificate. This note establishes, from vendor documentation and standards, which services and devices can do Ed25519 today, how comparable systems certify and revoke a short-lived key for offline verifiers, and what each custody option costs and risks. **Decision informed:** the key-custody ADR (`cto` decides; `security-lead` reviews custody and ASVS exceptions; the user decides) and the `/threat-model licensing` run. This note recommends and decides nothing.

## 5. Decision

**Recommended - pending user decision** (`security-lead` will review; the user decides; `cto` records the ADR). Nothing here is decided.

**Recommended: O1 as the shape, with its two weak points named, and O5's "two independent roots" as an alternative for the backup.**
- Two levels, as the founder proposed: the shape matches TUF and the IANA root (F414, F421), and the revocation answer for offline devices is expiry plus a root-signed epoch carried on the lease contact (F428).
- Issuing key in **AWS KMS** because it is the only managed service read that offers Ed25519 inside a vendor-run key service with a stated non-export property (F401); Google offers it only as software (F402), Azure not at all (F403). Pure mode enforced by IAM (F425). **Condition:** AWS must document that this key spec is HSM-protected, or `security-lead` must accept it as the "isolated security module" of ASVS 13.3.3 (F426); the page read does not say. If neither holds, the fallback is O6 (issuing key on a Kodelix-run YubiHSM 2) rather than GCP software.
- Root on **YubiHSM 2 v2.4** (Ed25519 signs raw data, documented M-of-N wrap-key backup, tamper-evident log, $650, F410, F411, not affected by YSA-2024-03, F416). The alternative **O5** avoids copying a key at all but rests on unverified PIV facts (F409).
- Two-person approval in the issuer workflow, not the KMS (F429). Separate keys per purpose (licence, update manifest, ETA certificate): the update key and licence key must be distinct (`security-baseline.md`, F224); the ETA key's algorithm is not in this note (F424 item 14).

**Why not the others:** O2 as written is impossible (F402). O2' makes the root a file on a machine and the issuing key software. O3 gives up the offline root and the no-device-update revocation the founder asked for. O4 cannot issue leases. O6 is the fallback, not the first choice, because it adds a service to run.

**ADR needed:** yes (key custody and hierarchy; also the certificate format and the trusted-time rule for expiry); owner `cto`, with `security-lead`.

## 6. Security Notes

- **Controls** (ASVS 5.0.0; IDs and wording from Part 2, F214-F217 and F114, looked up there in the official text; not re-fetched): **9.1.3** verification keys from trusted pre-configured sources (the pinned root, not the licence); **9.1.2** algorithm allowlist (pure Ed25519 only, F425); **9.2.2/9.2.3** purpose and audience tags (separate keys per purpose); **11.1.1** documented key-management lifecycle following a standard such as NIST SP 800-57 (F420); **11.1.2** cryptographic inventory (every root, issuing key and certificate listed); **11.2.2** crypto agility (algorithm id in the format); **13.3.1** secrets in a secrets-management solution that also destroys material; **13.3.2** least privilege on the signing identity; **13.3.3 (L3)** operations inside an isolated security module (F426); **13.3.4 (L3)** secrets expire and rotate (issuing-key certificate expiry, F428); **2.3.5 (L3)** multi-user approval for high-value flows (F429). MASVS does not apply.
- **Advisories:** Yubico index read 2026-10-17 (F415); **YSA-2024-03** affects YubiKey 5 below 5.7 and YubiHSM 2 below 2.4.0, not the lines that have Ed25519 (F416). No advisory search was run for AWS KMS/CloudHSM, Google Cloud KMS, Vault, Nitrokey (F424 item 13): `security-lead` or `appsec-engineer` to run OSV/GHSA/vendor-bulletin searches for the chosen service and firmware before the ADR. Libraries: unchanged from Part 2.
- **Abuse cases** (feed `/threat-model licensing`):
  1. *Stolen issuing key (cloud credential theft).* Attacker mints licences and leases until the certificate expires or devices see the new epoch (F428). Counters: IAM limited to the issuer role, pure-mode condition, CloudTrail alert on a Sign call from any other principal, short certificate validity, epoch bump.
  2. *Insider alone issues a free seat licence.* Counter: second-person approval in the issuer workflow (F429), signing role not usable by individual staff.
  3. *Loss or theft of one root token.* With O1 the second YubiHSM restored from the M-of-N backup recovers (F411); with O5 the second independent root recovers (F427). A thief needs the token PIN/authentication key as well: not sourced beyond the capability model.
  4. *Both root copies lost.* No device can accept a new issuing key: every device needs a signed app update with a new pinned root (the TUF "out-of-band" case, F414). Counter: backups in two places, tested restore.
  5. *Pre-hash confusion.* An `ED25519_PH_SHA_512` signature presented as a licence (F425). Counter: IAM deny, purpose-tagged envelope.
  6. *Rollback of the issuing key epoch.* An attacker replays an old signed lease from a revoked key to a device that never saw the epoch. Counter: highest epoch persisted, as with the lease sequence; offline devices stay exposed until the lease ends (F428).
  7. *Backup compromise.* O2' backups are files; O1 wrap-key shares must be held by different people (F411); a wrap-key holder quorum is the control.
  8. *Cloud account takeover or region outage.* Issuing stops (verification continues) or the key is abused; a runbook is needed (Part 2 § 8).
- **Threat model:** required: `docs/architecture/threat-models/licensing.md`; not written yet.
- **Legal:** nothing here interprets law. Whether signing-key custody outside Egypt (the nearest AWS regions are Bahrain, UAE, Cape Town, Tel Aviv; Google Doha, Dammam, Tel Aviv, Johannesburg, F413) raises any PDPL or ETA issue is **needs counsel**; no primary text was read, and a signing key holds no personal data by itself.

## 7. Performance & Caching Notes

- **Expected load:** a handful of signatures per tenant per lease renewal and a few seat licences a month (Part 2 § 7); three venues today. No figure sourced for growth.
- **Hot paths:** none on the counter. Signing is on the issuer side, off the request path; verification is on the device, cached per sequence (Part 2 § 7). A KMS or HSM call per lease renewal: latency unmeasured (PENDING - S403). Reference point only: Nitrokey 3's own factsheet gives 622 ms per Curve25519 signature, irrelevant to the cloud path (F417). CloudHSM PureEdDSA cap 16,000 bytes (F408): a lease is far smaller.
- **Caching candidates:** the issuing key's public key and certificate (in memory on the issuer and in the app); never cache signatures from KMS; the signed lease is a stored artefact. The root public keys are compiled into the app.
- **Budgets affected:** `docs/architecture/perf-budgets.md` is not present in this checkout; budgets "not checked". The 3 s counter ceiling is respected because no signing or certificate chain walk happens in a counter action: the chain is verified once per new lease sequence.
