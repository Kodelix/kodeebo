## 1. Question

ADR-0012 must decide, for the hosted Ktor 3.6.0 / Exposed 1.5.1 / PostgreSQL 18.6 backend on one 2-vCPU VPS with one developer:

1. **Where the work list lives and how work is claimed.** Options: the own transactional outbox with a per-tenant sweep (ADR-0006 design 2-a), the same plus a CP "pending work" list (2-d), or a JVM library queue (db-scheduler, JobRunr, Quartz). Also which ADR-0001 table class and role grants each option's tables need under FORCE RLS (registry stance FP-QUEUE-WITHOUT-ADR-R2).
2. **How recurring and delayed jobs are scheduled and retried on PostgreSQL alone.** This covers next-run columns, backoff, attempt limits, a dead state, at-most-one runner, and polling versus LISTEN/NOTIFY.
3. **Whether `stack.messaging` is set to `none`, and the founder's three revisit triggers.** The triggers are a second backend instance, many integrations and advanced search; for each, what it requires and the observable signal that fires it.
4. **Whether design 2-a works through Exposed `suspendTransaction` inside the ADR-0002 `withScope` helper.** This was executed before only on Go (bt-F208) and left unproven on JDBC (bt-F213, bt-F214).
5. **How a job loop is started and stopped inside Ktor 3.6.0.** bt-F215 left this NOT SOURCEABLE.

Per-part questions: § 3 and the appendices.

## 3. Findings

### Part 1 — work list and claiming; recurring, delayed and retried jobs

| # | Claim | Source (link) | Tier | Notes |

| F101 | **`FOR UPDATE ... SKIP LOCKED` (PostgreSQL 18, closes bt-F215's "not read").** A row that cannot be locked at once is skipped instead of waited on (`NOWAIT` errors instead). The docs warn that skipping gives "an inconsistent view of the data", unsuitable for general use, and recommend it for several consumers of a queue-like table. `NOWAIT` / `SKIP LOCKED` apply to row locks only: the table-level `ROW SHARE` lock is still taken normally. Locking stops once `LIMIT` is satisfied; rows skipped by `OFFSET` are still locked. At READ COMMITTED, `ORDER BY` is applied before locking, so after a wait the output can appear out of order (the docs' workaround is a locking subquery, which locks every row); at REPEATABLE READ / SERIALIZABLE the same case raises `40001`. The section says nothing about row-level security; it requires `UPDATE` privilege on at least one column of each locked table (so a role that only has `SELECT` cannot claim with `FOR UPDATE`). | [PG 18 SELECT, locking clause](https://www.postgresql.org/docs/18/sql-select.html) (fetched 2026-10-20, content via fetch-tool summary) | 2 | The RLS interaction is not on this page: see F124 (CREATE POLICY, tier 2) and the executed F111, F112. |
| F102 | **Row-lock lifetime and storage (PG 18).** Row locks are released at transaction end or when a savepoint is rolled back. They are not kept in memory (no limit on locked rows), but taking one can write to disk. Row locks do not block plain reads. | [PG 18 explicit locking, row-level locks](https://www.postgresql.org/docs/18/explicit-locking.html) (fetched 2026-10-20, via summary) | 2 | A claim transaction therefore holds its rows until it commits: the lock IS the lease, and a crashed worker's lock disappears with its connection. |
| F103 | **Advisory locks (PG 18).** Application-defined, not enforced by the server. Session-level locks are held until unlocked or the session ends and ignore transaction rollback; transaction-level locks release automatically at transaction end and have no explicit unlock. Locks share the main lock table, whose size depends on `max_locks_per_transaction` and `max_connections`. The docs warn that putting a locking function next to `LIMIT` in one query can lock rows that `LIMIT` later discards, and recommend a subquery for the `LIMIT`. | [PG 18 explicit locking, advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html) (fetched 2026-10-20, via summary) | 2 | A session-level lock held by a pooled connection survives into the next borrower: ADR-0002 forbids session state; use only the transaction-level form with the tenant helper. |
| F104 | **Advisory lock function names (PG 18).** Each takes one `bigint` or two `integer` keys: `pg_advisory_lock`, `pg_advisory_xact_lock` (blocking, exclusive), `pg_try_advisory_lock`, `pg_try_advisory_xact_lock` (return `boolean` at once), shared variants, `pg_advisory_unlock` and `pg_advisory_unlock_all` for session locks. The docs say a transaction-level lock cannot be released explicitly. | [PG 18 admin functions](https://www.postgresql.org/docs/18/functions-admin.html) (fetched 2026-10-20, via summary) | 2 | `pg_try_advisory_xact_lock(key)` is the at-most-one-runner primitive that needs neither a table nor a session. |
| F105 | **NOTIFY / LISTEN (PG 18).** Notifications are sent only after the sending transaction commits and are never delivered if it aborts. A listening session inside a transaction receives them only after that transaction ends. Identical channel+payload within one transaction collapse to one delivery; order follows commit order. Payload is a string under 8000 bytes by default (the docs suggest sending a key, not data). The queue is about 8 GB in a standard install; when it fills, `NOTIFY` fails at commit, and a long transaction in a listening session blocks queue cleanup. The page does **not** say whether notifications survive a listener disconnect, nor anything on poolers or hot standby. | [PG 18 NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html) (fetched 2026-10-20, via summary) | 2 | A wake-up signal can be lost while no session listens, so polling must stay as the floor (see F120). Survival across disconnect: NOT SOURCEABLE from this page; the LISTEN page was not fetched (budget). |

| F106 | **db-scheduler README details (v16.x docs).** Licence Apache (badge link), Java 17 minimum, Maven snippet 16.11.0 (stale against bt-F211's 16.12.0). Polling interval default 10 s; two strategies, `fetch` and `lock-and-fetch` (`select for update ... skip locked`, supported on PostgreSQL, SQL Server, MySQL 8+); "only one instance picks a given execution" by optimistic locking or select-for-update. Recurring tasks: after each run the `Schedule` gives the next time, and start-up creates the first execution only when none exists. Failure: `FailureHandler`; default for a recurring task is to reschedule on its schedule, for a one-time task retry after 5 minutes; **no dead-letter state** (max-retries and backoff appear only as example handlers); executions whose task name no longer resolves are deleted after `deleteUnresolvedAfter` (default 14 days). Heartbeat 5 minutes, 6 missed = dead, default `ReviveDeadExecution`. Immediate execution is off by default; **no LISTEN/NOTIFY**. The `scheduled_tasks` columns and DDL are not on the page (they are in `postgresql_tables.sql` under the test resources). Multi-tenant use appears only as "per-tenant recurring tasks"; nothing on RLS. | [db-scheduler README (raw)](https://raw.githubusercontent.com/kagkarlsson/db-scheduler/master/README.md) (fetched 2026-10-20, via summary) | 3 | Adds to bt-F203 (same source family). ## 5. Decision

**Decided by the user (founder), 2026-10-20**, from the options above (major decisions, `AskUserQuestion`):

1. **Work list: W1 now, W2 on a measured trigger.** Own `outbox`, `dedup` and `job_schedule` tables as TD under ADR-0001, a per-tenant sweep driven by `platform_rt`'s tenant list, claims with `FOR UPDATE SKIP LOCKED` through the Exposed DSL inside `withScope`. Polling, with retry, backoff and a `dead` status in the row. Recurring jobs as schedule rows claimed with a row lock. No session-level advisory locks. W2 (a CP hint, insert-if-absent, never a counter, plus a periodic full sweep) is adopted when a measured idle sweep crosses a threshold that ADR-0012 sets.
   *Why not the others:* W3 puts work rows in tables with no tenant key, polled by a role that would list tenants, so it needs an ADR-0001 amendment before any code. db-scheduler also lacks a dead state, and its Exposed transaction join is unproven. JobRunr 9.0.2 is one day old and dual-licensed. W4 breaks ADR-0001.
2. **`stack.messaging: none`.** The three revisit triggers and their signals (table above) go into ADR-0012. If a trigger fires, re-research NATS JetStream first, then RabbitMQ; Kafka only once its docs are sourced. CDC (Debezium) is a trigger-2 fallback.
   *Why not the others:* no broker removes an outbox duty (F224). Each adds a service, a relay and a second failure domain to one 8 GB host that already runs two JVMs during a deploy (F220). RabbitMQ's minimum exceeds the host (F212). Streams can lose acknowledged writes on failover (F207). Kafka could not be assessed (F218).
3. **Lease split by effect.** Effects that only touch the database run inside the claim transaction (C1). Effects that call an external provider (email, push, webhooks) use a committed lease column, a separate effect transaction and an idempotency key (C2).
   *Why not C2 everywhere:* reaper, expiry and heartbeat machinery that database-only effects do not need.
4. **S31 download approved and run.** 7,813,756 bytes of jars (F320). S31 and S31b replaced the PENDING Exposed and Ktor half with executed evidence (F322–F340).

**Carried to ADR-0012 as recommendations (the parts recommend them; the user did not decide them separately; `cto` decides in the ADR):**
- Set the job database's Exposed attempt count to 1 with `DatabaseConfig { defaultMaxAttempts = 1 }` (F336, F337).
- Order the timeouts: the helper's `transaction_timeout` < the runner stop timeout < Ktor `shutdownTimeout` (5000 ms default, F334).
- Set `client_connection_check_interval` on the job pool's connections (the pgjdbc `options` property, F339). A blocking JDBC statement is not interrupted by cancellation and keeps its rows locked after the JVM exits (F338).
- Lifecycle L2: start the `JobRunner` from `ApplicationStarted`, stop it from `ApplicationStopping`, close the pools in `ApplicationStopped`. Never use `ApplicationStopPreparing` (F329, F331).
- Add a catalogue-test rule that `job_rt` holds both a SELECT and an UPDATE policy on every work table, and alert on the oldest pending age, to catch a silently dark queue (F112).
- Make the job loop multi-instance safe from the first release, because deploys overlap (F220).
- Retry parameters, poll intervals and per-kind transaction budgets come from configuration with typed defaults (the spike's 30 s / 3600 s / 4 are placeholders, F117).

**Rests on unexecuted items (flagged, not accepted):**
- S31c: the stop test with `transaction_timeout` below the runner timeout (F341). **Executed 2026-10-21 and passed (F342–F347).** With 1,500 ms and 2,500 ms under a 3,000 ms runner stop, and no `client_connection_check_interval`, the server ended the statement, the join finished in time and the rows were free. The 6,000 ms control kept them locked about 2.4 s after JVM exit. Not covered: F346, F349.
- S12: the W2 hint-removal race. It matters only when W2 is triggered.
- Half-open connections: no FIN/RST was tested (F311).

**Follow-up record:** ADR-0012 (`/architecture-decision`), plus the `project.yaml` change `stack.messaging: none` once the ADR is accepted. Proposed pin: `ktor.pgjdbc: 42.7.14` (part 3 § 10), for the user to apply.

#### 5. Decision

**Recommended - pending user decision** (the caller records the final choice; `cto` decides in ADR-0012):

- **Area A: option A1 (design 2-a) now; A2 (2-d) as a named, measured step.** Reasons: A1 is the only option whose tables fit ADR-0001 without an amendment (TD tables, `job_rt` SELECT+UPDATE(+DELETE) policies, `app_rt` INSERT, no new role or class), it keeps the lease inside the transaction that already enforces the tenant (F111, F113), and it is the registry's stated direction (FP-QUEUE-WITHOUT-ADR-R2). Trigger to move to A2: a measured idle sweep on the Exposed path (S13, jobs-part-3) that exceeds a per-pass budget set in ADR-0012; when adopted, the hint must be insert-if-absent, never a counter (F115), with a periodic full sweep as safety net.
- **Area B:** polling (B1) as the floor with a typed-default interval per job class; no LISTEN/NOTIFY until a measured enqueue-to-start latency requirement fails (B2 then, with a poll floor, F120); retry in the work row (B3) with per-kind `max_attempts` and backoff parameters held in configuration, not code (coding-standards "no hardcoded business values"); `dead` is a status, alerted at count above 0; recurring jobs as per-tenant TD schedule rows claimed with a row lock (B4-i), an advisory transaction lock (B4-ii) only for a singleton loop that has no row; no session-level advisory locks anywhere; B5-i (lease = claim transaction) as the default with a per-kind transaction budget, B5-ii only for a kind that cannot fit its budget.
- **Why the others lost:** A3-A5 put work rows in a table with no tenant key, outside the tenant policy, polled by a role that would list tenants (F109, F110, ADR-0001) and need an ADR-0001 amendment before any code; db-scheduler additionally has no dead-letter state (F106) and its transactional enqueue is unproven on Exposed (bt-F203, bt-F214). Their real strengths (heartbeat, recurring schedules, less code) are worth revisiting if the job kinds grow beyond what about 200 lines of SQL and Kotlin handle, or if the service moves off one node. JobRunr 9.0.2 is one day old and dual-licensed (F122).
- **Proposed ADR-0001 entries (for `cto`, not applied):** `outbox`, `dedup` and `job_schedule` as TD; `tenant_work` as CP only if A2 is adopted; a catalogue-test rule that `job_rt` holds both a SELECT and an UPDATE policy on every work table (F112). No change to `pins.yaml`.
- **Decisions this rests on that were not executed:** the Exposed path (S13, jobs-part-3), the 2-d removal race (S12), the hung worker (S14). A decision resting on them is flagged, not accepted.
- **ADR needed:** yes, ADR-0012.

- **Abuse cases**: (1) *Forged or cross-tenant work item*: a work table outside the tenant policy lets a role inject or read another tenant's items (registry FP-QUEUE-WITHOUT-ADR-R2); with A1 a claim with no context saw 0 rows and an insert for another tenant was refused (F111, F114). (2) *Dark queue*: a missing UPDATE policy makes `FOR UPDATE` return nothing without an error (F112) and jobs silently stop (closure, retention, notices): needs the oldest-pending-age alert and a catalogue test. (3) *Poison item*: an item that always fails would loop forever; attempt limit, capped backoff and a `dead` status bound it (F117); dead rows hold payloads, so payloads should carry ids, not personal data, and dead rows fall under the ADR-0005 personal-data marker and retention. (4) *Replay and duplicates*: a re-run after a crash is expected (F118); consumers write a dedup row in the effect's transaction (bt-F208d). (5) *Tenant floods the queue* through `app_rt` inserts: a per-tenant pending-row cap and the one-batch-per-tenant-per-pass sweep keep other tenants served; the cap value is unspecified. (6) *Session-level advisory lock* held by a pooled connection blocks a job on another request's connection (F103, F119): forbid it. (7) *NOTIFY channel abuse* if LISTEN is adopted: who may send is NOT SOURCEABLE from the NOTIFY page (F105), so treat a notification as a hint to poll, never as an instruction carrying data. (8) *Operator requeue of dead items* is a privileged action over tenant data: path undecided (section 9).
- **Threat model**: no new file proposed; the work-list abuse cases above belong in the existing ADR-0005 closure/erasure and ADR-0007 owner-notice threat models; `security-lead` decides.

#### 5. Decision

**Chosen: Recommended - pending user decision** (the caller records the final choice; `cto` decides in ADR-0012).

- **Area A: A1** through Exposed `suspendTransaction` inside `withScope`, claim by the Exposed DSL. Move to **A3** when a measured idle sweep is too slow (threshold for `performance-engineer`).
- **Area B: B2**. Start the runner from `ApplicationStarted`; stop it from `ApplicationStopping` with its own timeout; close the pools in `ApplicationStopped`. Do not use `ApplicationStopPreparing` (its order is known, F329, its meaning is not documented). B1 is an acceptable fallback for cooperative work, with the drawbacks in the table.
- **Area C: C1** for DB-only effects; **C2** for effects that call external providers (part 1).

**Conditions.** (1) Set the attempt count of the job database to 1 (`defaultMaxAttempts = 1` in its `DatabaseConfig`, or `maxAttempts = 1` in the block): S31b shows the block then runs once and fails in about the timeout, while the default of 3 re-runs it (F336, F337). (2) Order the timeouts: helper `transaction_timeout` < runner stop timeout < Ktor `shutdownTimeout` (default 5000 ms, F334); coroutine cancellation does not interrupt blocking code, so otherwise the JVM exits with work in flight (F332). (3) Bound every blocking statement on the server side: cancellation does not interrupt a JDBC statement and the JVM exits with it running, leaving the rows locked until it ends (F338); `transaction_timeout` below the runner stop timeout (the combination was not run, F341) and `client_connection_check_interval` on the job connections (F339) bound it. (4) Set `client_connection_check_interval` on job connections where a worker can sit in a long statement (F311). (5) An effect that calls an external provider must be idempotent (dedup row) because a stop or kill can end it between the call and the commit.

**Why not the others.** A2 breaks ADR-0001. B1 leaves drain time and expiry to Ktor internals and `@InternalAPI` (F314). Closing the pool earlier is wrong (F331). B3 adds a deployable nothing requires yet (revisit: web restarts must not interrupt jobs, or job load shows in request latency). C2 everywhere is more machinery than DB-only effects need.

#### Question

Does a stop during a blocking JDBC statement end inside the stop window and free the claimed rows **without** `client_connection_check_interval`, when the `withScope` helper sets `transaction_timeout` below the runner stop timeout, with attempts = 1? Decision informed: ADR-0012 Decision 7 (timeout ordering), acceptance blocker 1. Decider: `cto` / founder. This note recommends only.

#### Result for ADR-0012 blocker 1

**Passes, as executed on loopback with a process stop (SIGTERM).** With `transaction_timeout` 1,500 ms (Rc1) and 2,500 ms (Rc2), both below the 3,000 ms runner stop timeout and the 4,000 ms `shutdownTimeout`, and the pool without `client_connection_check_interval` (the session printed `[0]`): the server ended the blocking `pg_sleep(12)` itself with SQLSTATE 25P04, the runner join completed inside its timeout (775 ms and 1,852 ms), `ApplicationStopped` followed, the JVM exited, and the claimed rows were claimable again at the first sample after the server's kill. The body ran exactly once in every case (attempts = 1 held through the stop path). The control (Rc3, `transaction_timeout` 6,000 ms, above the stop timeout) reproduced the jo-F338 behaviour: the runner stop timed out at 3,001 ms, the JVM exited, and the rows stayed locked for about 2.4 s after JVM exit, until the server's timeout killed the session. So Decision 7's ordering rule (helper `transaction_timeout` < runner stop timeout < `shutdownTimeout`) is supported and does not need revising for this combination. Two qualifiers belong in the ADR: (1) `transaction_timeout` counts from the start of the transaction, so the worst case from SIGTERM to the server's kill is the full helper timeout (SIGTERM just after the claim); Rc2 had 1.84 s left at SIGTERM, and the worst case 2.5 s still fits under 3.0 s (calculation, not a run); (2) not covered: a host loss or partition, a worker that is idle in a transaction on JVM-side work (the timer should apply, untested here), and Rc runs of a CancellationException caught inside the statement (see F346).
