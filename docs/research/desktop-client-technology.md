## 1. Question

Which technology should the Kodeebo Windows cashier app be built on? The app is the counter of an offline-first point of sale for PlayStation lounges and cafés in Egypt. Its local encrypted store is the source of truth; it prints Arabic ESC/POS receipts and opens the cash drawer; it syncs in the background to the hosted multi-tenant server; it updates itself and is code-signed; it is installed on the venue's PC by Kodelix staff and used by a tired, non-technical cashier in Egyptian Arabic. Windows 10/11 is the primary target. Windows 7 x64 is best-effort and reported separately: failing on Windows 7 does not by itself eliminate an option. Two secondary questions: how much code each option shares with the owner Android app (Tier 1, D6) and the owner web dashboard, and — never as a ranking input — whether it could later serve an Android cashier (Later, decided 2026-10-16). The note also plans the `/prototype` spike on real Windows 10/11 and Windows 7 x64 machines (section 9, Spikes).

The founder decides, through `/architecture-decision`, after the spike; the answer becomes `stack.desktop` in `/setup-stack`. This note recommends and decides nothing. **Out of scope**: the sync protocol, conflict policy and money correctness (separate local-first-sync `/research`), Egyptian e-receipt/VAT rules (separate `/research`), the N5 grace length (`/license-design`).

Parts: 1 runtime/UI shell and Windows version support · 2 local encrypted storage and the background-sync execution model · 3 receipt printing, Arabic output, cash drawer · 4 code signing, auto-update, installer · 5 code sharing.

## 3. Findings

Merge observations that read across the parts (each rests only on the cited rows):

- **M1 — Modern .NET on Windows 10.** The .NET install page supports .NET 8/9/10 on Windows 10 only for LTSC and Enterprise editions (F13). A venue PC on Windows 10 Home/Pro is outside .NET 10's supported set, and Avalonia's desktop floor is .NET 8 (F26), which ends on 2026-11-10 (F14).
- **M2 — The Windows 10 window is closing for every stack.** Home/Pro has been out of support since 2025-10-14 (F2, F211); consumer ESU runs to 2027-10-12 (F211); Edge/WebView2 keep updating on 22H2 to at least October 2028 (F5); Qt 6.12 is the last Qt with Windows 10 (F20).
- **M3 — Tauri on Windows 7: sources conflict.** Tauri's prerequisites page says Windows "7 and later" (F415), and its installer page gives Windows 7 instructions (F12). The maintainers' RFC #12550, closed 2026-06-23, says 2.11 is the last semi-official Windows 7 version and that from 2.12 support "is no longer guaranteed" (F11). The newer maintainer statement governs the current 2.12.4; the docs pages were not reconciled with it. S3 settles it.
- **M4 — Option A carries the most unresearched duties on the cashier PC.** On the JVM, the only encrypted-SQLite route found is a community fork that is "maintained, but not actively developed" (F109), and its SQLDelight route rests on a tier-5 lead (F108). Raw spooler printing on the JVM was not researched (§ 3.3 per-runtime table). No JVM updater was researched, and Velopack's Java SDK is only "planned" (F329, F341).
- **M5 — Tauri has the most documented hardware and update path.** The Rust `escpos` crate covers spooler-free USB via `usbprint.sys` with status read-back (F213, README-level, unrun), and the updater makes an update-signature check mandatory, with server-side rollout and rollback (F320–F322). Against that, it adds Rust to the team and its Windows 7 guarantee is gone from 2.12 (F11).
- **M6 — Electron's update path is researched but carries an unread advisory.** electron-updater supports staged rollout and Authenticode checks (F324–F326), but GHSA-9jxc-qjr9-vjxq, an electron-updater code-signing bypass on Windows, is still unread (F347). Printing needs a native module (F212, F218), and Electron shares nothing with Android (F413).
- **M7 — Windows 7, every route.** The routes are Electron 22 (F7), Qt 5.15 (F21), Tauri ≤ 2.11 with WebView2 109 (F11) and a Chromium 109 shell (F10). Each is a browser or UI engine that no longer gets security fixes, holding money data. The PC also needs KB4490628 + KB4474419 for SHA-2 signatures (F29, F311) and KB3140245 plus Schannel settings for TLS 1.2 (F30).
- **M8 — Code signing does not depend on the runtime.** Microsoft's Artifact Signing (Public Trust) is not open to an Egypt-based company (F301, F302). An OV certificate on a hardware key is mandatory under the CA/B Forum rules (F308). EV certificates no longer give a SmartScreen advantage (F305).

## 5. Decision

**Chosen (interim, founder, 2026-10-16)**: the spike shortlist is **A (Compose Multiplatform Desktop), B (Electron) and C (Tauri 2)**. No runtime is chosen yet. The final runtime is chosen after spike phase 1, through `/architecture-decision`.

- **Phase 1 result and C not run (founder, 2026-10-17)**: spike round 1 ([prototypes/desktop-client-spike/README.md](../../prototypes/desktop-client-spike/README.md), commit 9b7abd6) found that **A and B both pass G1 and G2** on the 4 GB throttled VM: per-user install with no elevation, 20/20 RAW prints byte-identical at the sink, 0 of 100 hard kills corrupting the encrypted store, and every close under the 3 s ceiling after a reboot once native libraries load before the first sale. **C (Tauri 2) is not run.** Reason: B already covers the web shell this note asked for (A plus at least one of B or C), and C's main advantage, a smaller install that uses the PC's WebView2, matters less with A installing at 136 MB. Printer status reading, C's other draw (Rust `escpos` with `DLE EOT`, F213), is runtime-neutral, so it becomes spike **S50** for A and B on the real-printer day (§ 9 Spikes) instead of a reason to build C. C stays on record as an option if A and B both fail a later gate.
- **Why these three**: together they cover both sharing directions — a Kotlin owner Android app (A) and the web dashboard (B, C) — and both web shells. A and C are the two most-documented ends of the trade-off: stack fit (A) against printing and update coverage (C).
- **Why not the others (for this product)**:
  - D (.NET 10): supported on Windows 10 only for LTSC/Enterprise, while venue PCs are likely Home/Pro (M1, F13).
  - E (Avalonia): the same problem, with a desktop floor of .NET 8, which ends 2026-11-10 (F26, F14).
  - F (Qt): C++ would be a third language for two engineers; closed-source licence terms need counsel; 6.12 is the last Qt with Windows 10 (F20, F22).
  - G (Flutter) and I (React Native for Windows): a new language or a lagging port, sharing only the contract with a Kotlin Android app or the React dashboard (F410, F416).
  - H (Go shell): useful only if `stack.backend` is Go, which is undecided; Windows 10 floor (F24).
  - J (kiosk/PWA): no spooler RAW printing; needs a local helper for the printer (F219).
  - None of these is proven worse on performance: nothing is measured. Any of them can return if phase 1 rules out all of A, B and C.
- **Windows 7 x64 — not supported in Tier 1 (founder, 2026-10-16)**: the one venue (of 3) still on Windows 7 has its PC or Windows upgraded by Kodelix during the on-site install. Spike phase 3 is not run. The Windows 7 findings (F6, F7, F10, F11, F29, F30, F311, M3, M7) stay on record for a later decision, if a paying customer needs Windows 7.
- **Windows 10 — supported in Tier 1 (founder, 2026-10-16)**: unlike Windows 7, every shortlisted runtime still supports Windows 10, so the app keeps getting patched there. At the on-site install, a Windows 10 PC moves to Windows 11 when its hardware meets Microsoft's requirements (F501); otherwise it is enrolled in consumer ESU. Windows 11 is never forced. **Reversal trigger:** revisit Windows 10 support before consumer ESU ends on 2027-10-12 (F211). Recorded in the product brief's decision log.
- **Gap classification (founder confirmed)**: no `NOT SOURCEABLE` gap blocks the spike. OQ8 (JVM store, printing and updater), OQ9 (advisories) and OQ11 (licence texts) block the runtime ADR. OQ10 (ASVS/MASVS IDs) blocks the threat models.

**What the researchers recommend (each on its own slice):**
- Part 1 (runtime): shortlist **A** as the lead, **B** as the alternate if web-skill reuse matters more than stack alignment, **D** as the native fallback. All of this is conditional on S1, S6 and S7 on a low-spec Windows 10 22H2 PC.
- Part 5 (sharing): **A** if the owner Android app (D6) is built in Kotlin; **B or C** if the cashier should share the web dashboard instead.
- Part 3 (printing): printing does not separate the native families. It counts **against J** (no spooler RAW, F219).
- Part 2 (storage) and part 4 (signing/update): independent of the runtime (§ 4.2). For update and printer access, part 4 found researched paths only for B and C (F320–F326).

**What the merge adds:** A wins on stack fit and Android sharing, but it carries the most unresearched cashier-PC duties: encrypted store, RAW printing and updater (M4). #### 5.1.2 Part 2 — storage and sync execution

**Chosen**: Recommended - pending user decision. The founder decides via `/architecture-decision`.

- **Storage**: A1 or A2 (SQLite with whole-file engine encryption) over A3/A4. A1 has the better-documented behaviour (F101-F104) and A2 is the only JVM route with Windows natives found (F109), so the choice follows the runtime chosen by the other researchers. A3 loses on leakage and the "no custom crypto" baseline; A4 was not researched; A5 only if A1/A2 fail S10.

#### 5.1.3 Part 3 — printing and drawer

**Recommended - pending user decision.** From the printing/drawer side only; the founder decides the runtime with the sibling parts via `/architecture-decision`.

- Printing does **not** decide the runtime among native families. Every candidate that can call Win32 can do the RAW spooler write from Microsoft's own sample (F216); .NET, Qt, Rust and C++ do this first-class, Flutter has a plugin (F220), Electron and the JVM need a native module or helper whose maintenance I could not confirm (F212, F214, S20). Printing is a **negative** factor for a pure Chromium kiosk/PWA shell: it has no spooler RAW and only serial/USB limits (F219, S28), so it would need a local helper.
- Transport: design a `ReceiptPrinter` port with adapters for T1 spooler RAW (default on a driver-equipped Windows 10/11 PC), T4 TCP 9100 and T3 COM; add T2 direct USB only if S22 proves it. Keep T4/T3 in the design because they avoid the driver and print-policy risk (F209) and are the likely route on Windows 7.
- Arabic: start with R1 (raster) as the default because it needs no per-model code-page table (F206) and the shaping is under our control; keep R3 as the optimisation once S24 proves a model's code page and shaping. Do not rely on R2 until S24 passes on real printers.
- Drawer: D1 through the printer; status D2 where the transport is bidirectional, D3/D4 otherwise, and log every kick (see section 6).
- Why the others lost: R2 depends on unknown firmware shaping and per-maker numbering (F206, F223); R4 needs drivers (F209); T5 and a pure web shell cannot reach the spooler (F219).
- Conditions: S20-S29 results on real hardware, and the founder's list of printer/drawer models in use (Open questions).
- ADR needed: yes (printing adapter port, supported-hardware matrix, Arabic rendering path). Follow-up record: ADR via `/architecture-decision`.

#### 5.1.4 Part 4 — signing, update, installer

**Chosen**: Recommended - pending user decision. The caller and the founder decide via `/architecture-decision`; this part does not choose the runtime.

**Why (recommendation, based on findings only)**
1. **Signing**: Option B, an OV certificate from a CA that accepts the Kodelix legal entity, with the key in a token or CA cloud HSM, because Artifact Signing is not open to Egypt (F301, F302) and EV buys nothing for SmartScreen (F305). Sign every PE (app, updater, helpers) and the installer with a timestamp, and always with the same publisher identity so reputation carries across releases (F305, F306). Expect SmartScreen warnings for the first venues and plan staff-installed first runs around that (F305). Depends on Q-302.
2. **Update**: choose the runtime first (other parts), then require of its updater: a signature check that does not depend on the Windows version, server-side staged rollout and rollback, per-user no-admin apply, download-in-background and apply only when no shift is open. From what was fetched, both Tauri 2 (own update key, F320-F322) and electron-updater (Authenticode + hook, F324-F326) can meet these; the rest are unresearched (F341). **Licence-blocked options**: none (hosted-only; L1-L4/T1 concern customer bundles).

## 6. Security Notes

- **Controls**: ASVS 5.0.0 / MASVS 2.1.0 / API Top 10 2023 requirement IDs are **NOT SOURCEABLE** in all five parts; none of the official documents was fetched. The only normative source used is the CA/Browser Forum Code Signing Baseline Requirements 3.11.0 (F308). Areas to map: local store encryption and key custody, update integrity and signing, client-side licence and clock-tamper checks (N5), TLS to the server, drawer-kick audit, spool and receipt data.
- **Advisories**: OSV run on 2026-10-16 found no advisories for Electron 44.8.0, Tauri 2.12.4, Ktor client 3.6.0, Capacitor 8.5.3, React Native 0.88.0/0.84.0, openapi-generator 7.26.0 or SQLDelight sqlite-driver 2.4.1 (F426). GHSA-9jxc-qjr9-vjxq (electron-updater code-signing bypass on Windows) was found but not read, and its output was not saved (F347). SQLCipher 4.19.0 fixed two low-risk issues, so no earlier version should be pinned (F102). The SQLite WAL-reset bug affects 3.7.0–3.51.2 (F106). **Not searched:** Compose Multiplatform, the Kotlin compiler, .NET, Avalonia, Qt, Flutter, Wails, Fyne, SQLite3MC, the Willena fork, Rust `escpos`, `node-thermal-printer`, Velopack, WiX and Inno Setup.
- **Platform facts**: Windows 7 gets no OS or browser-engine patches (F1, F6, F10). Electron 22 has been end of life since 2023 (F7). Windows 10 Home/Pro has been out of support since 2025-10-14 (F2). The print spooler runs as SYSTEM and loads third-party code; Windows protected print mode blocks third-party drivers (F209).
- **What encryption protects** (part 2, F101, F112, F114): a stolen disk, if the wrapped key cannot be unwrapped off the machine. Curious staff, only if they cannot run code as the key's Windows user. **Not a local administrator.** For money and N5 the cashier PC is untrusted, so integrity must be provable on the server.
- **Abuse cases (merged)**:
  1. Staff copy the database folder, or replay an old copy to undo a day.
  2. The clock is set back to extend the N5 grace.
  3. The PC is imaged or stolen with the wrapped key on the same disk.
  4. A power cut during close-bill or during an update corrupts data.
  5. A local password reset orphans the DPAPI key (lead F116).
  6. Unencrypted SQLite temp files or crash dumps leak data.
  7. The drawer is opened without a sale: every kick must go through one audited path with a reason. The drawer's own key still opens it.
  8. Another program on the LAN sends `ESC p` to a printer listening on port 9100.
  9. A stolen signing or update key pushes a malicious build to every venue.
  10. A spoofed update server downgrades the app to an older build.
  11. A tampered installer is carried on staff USB sticks.
  12. An unpatched Windows 7 engine (Electron 22, Chromium 109) is exploited.
  13. A web-view shell exposes the printing and drawer bridges to injected script.
- **Threat models required**: `/threat-model` for the local store and key custody, N5 time and grace, update signing, and drawer actions with the audit trail. None is written yet.

## 7. Performance & Caching Notes

- **Expected load**: one cashier PC per branch (MVP), 5–20 stations per venue (assumption), human-speed actions plus background sync, one receipt per sale. Venue PC spec unknown; low spec is treated as the risk.
- **Hot paths**: cold start (including key unwrap, F101); start session, add item, close bill, each a local transaction (commit durability, F106); receipt render, send and kick off the UI thread (`WritePrinter` is synchronous, F201); update download and verify must never delay a counter action. None of this is measured; it is pending S1/S40, S7/S43, S10 and S38.
- **Budgets**: `docs/architecture/perf-budgets.md` does not exist, so every budget is "not checked", never "met". Proposed items: cold start, counter-action p95 on the reference PC, idle memory, installed size, raster receipt bytes (F225: about 72 bytes per dot row at 576 dots).
- **Caching candidates**: the local store is the source of truth, not a cache. Candidates are the rasterised logo per (hash, paper width), the per-model printer profile, in-memory read models of prices and open sessions, the update manifest (short TTL + ETag), and versioned installers (immutable). A written decision goes through `/cache-design` once the sync design exists.

**S50 — printer status read from A and B (added 2026-10-17, founder; real-printer day).** PENDING — S50. *Hypothesis:* both A (JNA) and B (koffi) can read `DLE EOT n` status (n = 1 printer, 2 offline cause, 3 error cause, 4 paper sensor; F204) from the U.POS AI-330 and the Xprinter XP-80C and see paper out and cover open. *Why:* the 6-byte gap in the research's fake printer (F226) was exactly two such queries, and the money trail needs to know a receipt did not print. *VM/OS:* Windows 10 22H2 (and Windows 11 when its VM exists). *Hardware:* the two borrowed printers, USB, plus their LAN or serial port if they have one; cash drawer on the printer. *Steps:* (1) find a bidirectional path per model: the spooler RAW queue cannot read back (F208), so open the USB printer's device handle directly (Win32 `CreateFile` + `WriteFile` + `ReadFile` on the `usbprint.sys` device, the runtime-neutral form of S22), or TCP 9100 / COM if present; (2) from A and from B send `10 04 01` … `10 04 04` and record the reply bytes; (3) repeat with the cover open, with paper removed, and with the printer switched off; (4) check that printing through the spooler queue still works while the status path is open. *Pass signal:* for each model and runtime the status bytes change with cover open and paper out, the meaning of each bit is recorded against the vendor manual, and the transport that worked is named; if a model gives no status on any path, that is recorded as a hardware finding, not a runtime failure.
