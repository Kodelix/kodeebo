## 1. Question

ADR-0013 (decided by `cto`, the founder choosing; input from `integrations-engineer` and `security-lead`) must fix how Kodeebo sends notifications. **Email (part 1):** the JVM mail library (licence, maintenance, version to pin, advisories); what "provider accepted" means for SMTP under ADR-0012's external-effect contract (reply classes, partial recipient rejection, the lost-reply case, whether a Message-ID built from the item id helps); timeouts and retries that fit ADR-0012's lease and stop timeouts; bounce/DSN handling; a send-rate cap so a broken job cannot flood the founder's server; the SMTP credentials as a 0400 secret file per ADR-0009 Decision 3a; technical notes for GCC recipients later. **Push (part 2):** Web Push (Push API + service worker + VAPID) for the owner dashboard PWA versus FCM for a Play-listed wrapper (Capacitor or TWA) while OQ6 is open — what the backend sends in each OQ6 outcome, which sender, which responses mean done / retry / dead / delete the subscription, lifecycle, payload, TTL and urgency, delivery in Egypt. **Remote approval (part 2):** what a push may carry, how the approval returns, what happens when push is late, lost or stale, and whether remote approval can sit on a counter path under the 3 s ceiling. Both halves also feed the `auth_notices` claim/ack functions that ADR-0012 hands to ADR-0013 (amending ADR-0001 § 1c).

| F101 | RFC 5321 s3.3: each RCPT is answered on its own (250 accepted, 550 for a known-bad mailbox). DATA is refused (503/554) only when there was no MAIL or no valid RCPT; otherwise the server answers 354 and takes the message, so **a 250 after DATA can follow some rejected recipients**. **Cross-part point (both parts, independently).** ADR-0012 Decision 5, external effects, step 4 reads: "Because the item id is the provider key, a duplicate call is absorbed by the provider." Neither channel does that. SMTP is at-least-once with possible duplicates after a lost reply to the end of DATA (F112); a stable Message-ID is not de-duplication (F106). Web Push and FCM have no send idempotency key in what was read (F218). The contract still works (stable key, guarded tx B, re-run), but step 4 must say what absorbs the duplicate: nothing for mail (a second email is the accepted cost), the client for push (one notification per notice id). Part 1 adds a second gap: a rate-capped or breaker-deferred item must not spend an attempt, and ADR-0012's tx A always does `attempts + 1`.

## 5. Decision

**Chosen** — founder (Kamel Mohamed), 2026-10-21, input to ADR-0013 (`cto` decides the ADR; the founder decides OQ6). The researchers' recommendations stay as written in the appendices; where the founder changed one, this section governs.

**Email**
1. **E1 L-A: Angus Mail 2.0.5** behind a `MailSender` port, with the explicit settings of part 1 § 5 item 1 (timeouts, `starttls.required`, server identity check, fixed EHLO name, one recipient per message).
2. **E2 A-A:** "done" = the 250 reply to the end of DATA. An I/O failure after the message was sent and before its reply is retried with the same item id and Message-ID; a duplicate email is accepted. Classification by reply code and stage, never by Angus's lists (part 1 § 5 item 3).
3. **E5 N-A:** one notice per claim and per acknowledge, each with its own lease token.
4. **E3 changed — B-B in the first email story, not later.** An automatic bounce reader (IMAP poll of the bounce mailbox, RFC 3464 DSN parse) marks the address as **failing** and alerts the owner. Consequences carried into ADR-0013:
   - The bounce mailbox is shared by all tenants, and `job_rt` reads one tenant per transaction, so a bounce must name its tenant: the Message-ID (or the envelope sender) carries the tenant id and the item id as opaque ids, never an address.
   - The reader is a recurring job that reads an outside source, then marks the address under `withScope(Job, tenant)`; its shape (a platform-level kind, not a per-tenant sweep) is ADR-0013's to state.
   - A second credential (the mailbox account, or the same SMTP account) as a 0400 secret file per ADR-0009 Decision 3a.
   - Forged bounces are now in scope (F105 s4.1): a bounce counts only when it matches a recent item; it marks the address failing, it never deletes it.
   - Open: the mailbox protocol the founder's server offers, and the artifact that carries Angus's DSN classes (F128).
5. **E4 changed — the caps protect the domain's reputation, not the host's limit** (the founder's host allows about 1M messages a month, founder 2026-10-21). Global and per-tenant caps are set from the expected volume (recovery, alerts, invites) with a safety margin, in config; sends are **paced evenly**, not in bursts; a held item is **delayed, never dropped** (it spends no attempt, see item 10), and hitting a cap alerts. A held mail row is still subject to ADR-0012's 90-day pending expiry; reaching that age while held is itself an alert condition, and ADR-0013 states which rule wins.
6. **Move triggers for email** (when to leave the founder's own server): only measurable signals; no "before the first paying customers" trigger (founder, 2026-10-21). ADR-0013 lists them.

**Push and remote approval**
7. **P1 C:** one `PushSender` port, Web Push adapter first, FCM adapter only if OQ6 lands on Capacitor or native; no push at MVP (row 22 is email plus in-app).
8. **P2 changed — maintained library for the crypto, our request.** The maintained web-push library (`nl.martijndwars:web-push`, candidate 5.1.2) does the RFC 8291 encryption and the RFC 8292 VAPID signature; the request goes through the pinned Ktor client and the core outbound guard (item 11). ### 5. Decision

**Recommended - pending user decision.** ADR needed: yes (ADR-0013, a `cto` decision; this note is evidence).

**Chosen (recommended)**: L-A, A-A, B-A with a stated revisit trigger, R-A, N-A. A hosted provider (L-D) is ruled out by the founder's own server.

**Why**: Angus Mail is the reference Jakarta Mail implementation under EPL-2.0 (F118), has a clean advisory record at 2.0.5 (F119, F120), exposes every property we need (F122) and shows its reply handling in source (F123). The per-stage detail is what the retry-or-dead decision needs. "Accepted" is exactly the 250 to the end of DATA, the point where RFC 5321 says the server takes responsibility (F101, F110). SMTP cannot give exactly-once (F112), so ADR-0012's contract (a stable key, a guarded tx B, an at-least-once re-run) is the right frame and the duplicate cost is a second email. A stable Message-ID is RFC-conformant (F106) and makes a returned bounce traceable (F105), but it must **not** be presented as de-duplication: the RFC puts no duty on receivers.

**Why not the others**: L-B adds churn and hides stages. A-B can lose a gated notice. B-B and B-C need facts about the founder's server that are not known (F126) and add inbound attack surface; B-A is enough for owner alerts at MVP volume. R-B lets one tenant starve the rest; R-C needs a new table class. N-B cannot give per-notice acceptance.

**Follow-up record**: ADR-0013 (and an ADR-0012 amendment for the "before the claim" gate and for deferred items spending no attempt).

**Recommended design, derived.** The numbers are typed config defaults proposed here, not sourced; S13 (PENDING) must validate them.

1. Library settings, all explicit: `connectiontimeout` 5 s, `timeout` 20 s, `writetimeout` 20 s, `starttls.required` true (or `ssl.enable` true on an implicit-TLS port), `ssl.checkserveridentity` true, no `ssl.trust` wildcard, `mail.smtp.localhost` set to a fixed FQDN, `mail.smtp.from` set to the bounce mailbox address, `sendpartial` false, one recipient per message (F122).
2. Whole-send deadline 60 s, enforced by a watchdog that closes the transport. Socket timeouts are per read, so about a dozen reads could add up to minutes, and coroutine cancellation does not interrupt a blocking socket call (the jobs note found this for JDBC, `docs/research/jobs-and-outbox.md` F338). No in-call retry: the job-level backoff is the only retry. So `leaseDuration` of 120 s satisfies ADR-0012's "exceeds provider timeout plus retry budget" (F121). On a runner stop (ADR-0012's stop budget is seconds, far under 60 s) the sender closes the transport; the row stays `running` until its lease expires and is then claimed again (F121). RFC 5321's 5-minute and 10-minute figures are minimums for relaying MTAs (F111, F113), not targets for a submitter.
3. Classification, by reply code and stage, never by Angus's valid/invalid lists (F123):

| Stage / reply | Class | Job outcome |
|---|---|---|
| 250 to the end-of-data dot | accepted | tx B done; log item id only |
| Connect, TLS, greeting or EHLO failure or timeout; 421; any 4yz before the dot; 4yz to the dot | transient | retry with backoff, attempt counted (F109, F110) |
| I/O failure or timeout after the dot was written, before its reply | ambiguous | retry with the same item id and Message-ID; counter `ambiguous`; duplicate possible (F112) |
| Authentication refusal, MAIL FROM refused, STARTTLS missing, certificate failure | provider configuration fault | not dead per item: open the circuit breaker, alert; items wait. AUTH reply-code values (RFC 4954) NOT SOURCEABLE here (F127) |
| 5yz to RCPT (one recipient) | rejected_permanent | `Dead(recipient_rejected)`; ADR-0007 M31 gating pauses the gated change and alerts the operator. A 552 here is permanent by class (F109) although Angus lists it as unsent (F123): reviewer to confirm |
| 5yz to DATA or to the dot | rejected_permanent | `Dead(message_rejected)`; do not resend without review (F110) |
| Rate cap or open breaker (before the claim) | deferred | no attempt spent; needs an ADR-0012 hook (open question) |

4. Retry: ADR-0012's placeholders (30 s / 3600 s / 4 attempts) are short for mail if the server is down. With that base and cap, eight attempts span roughly 63 minutes at jitter 1.0 and about half at 0.5 (arithmetic: 30+60+120+240+480+960+1920 s). Per-kind `max_attempts` should come from the notice's useful life (recovery link expiry; the M31 bound in ADR-0007): owner `security-lead`.
5. One recipient per item, so partial recipient rejection cannot arise at message level. A notice to several owner contacts is several items, each keyed by notice id and contact id (a typed key, never an address or a hash of one, per ADR-0012 Decision 4).
6. Bounces: B-A at MVP. Revisit when an M31-gated change stalls because of an unseen bounce, or when hard bounces pass a threshold the founder sets.
7. Rate cap: R-A. The per-tenant budget lives in the per-tenant sweep, which already visits one tenant per transaction (ADR-0012 Decision 3a); the global bucket is per instance. Values are the founder's, bounded by the server's limits (F126).
8. `auth_notices`: N-A. Columns mirroring the `job_outbox` external-effect columns (status, `lease_until`, `lease_token`, attempts, error class) are needed on the PL table; signatures are ADR-0013's.
9. Credentials: see s6 and s9. The password is read from `/run/secrets/<name>` at start by a reader that fails start-up if the file is missing, empty, not owned by the process UID or not mode 0400. The user name is configuration, not a secret.
10. GCC later (technical only): ASCII mailbox addresses at MVP, validated before use (also the injection defence, F119). Arabic Subject, display names and body ride on MIME encoding with UTF-8 and need no SMTPUTF8 (F108; the Subject case is unconfirmed there; RFC 2047 NOT SOURCEABLE, F127). Non-ASCII mailbox names (RFC 6531/6532) need SMTPUTF8 on the whole path, and Angus has a code path for it whose switch is unconfirmed (F122, F108). IDN domains in A-label form: NOT SOURCEABLE (F127). Right-to-left layout of HTML mail: not researched.

### 5. Decision

**Recommended - pending user decision** (the founder decides OQ6; `cto` decides ADR-0013).

1. **Channel strategy: Option C.** Define one `PushSender` port in `notify` with two adapters selected by the subscription's `kind`. Build the **Web Push adapter first** (it serves the default OQ6 path and a TWA); build the **FCM adapter only when the Capacitor or native outcome is chosen** after S32/S33. No push ships at MVP: row 22 (owner-alerts) is email plus in-app, push is Beta (row 23).
2. **Web Push sender: lean W2** (own adapter over the single egress client), **provided S22 shows the encryption reproduces the RFC 8291 test vector**; fall back to W1 (using only its encryption class, or the whole library if its HTTP client can be forced through the allowlist) if S22 fails or the team does not want to own the crypto. Reason: SSRF control and one timeout/breaker policy matter more than the saved code (F219). Both are low-confidence until S22 and F220i are done.
3. **FCM sender: lean F1 (Admin SDK) if its dependency set is acceptable, else F2**; the choice waits for F220j/k and F205. Credential: the service-account JSON and the VAPID private key are **0400 files owned by the backend container's UID, mounted at `/run/secrets/<name>`** (ADR-0009 Decision 3a; F206, F217), never environment variables or the image. The Admin SDK reads a path (`GOOGLE_APPLICATION_CREDENTIALS`, F206), which fits a mounted file.
4. **"Provider accepted" (ADR-0012 contract):** Web Push = HTTP **201** from the push service (F202). FCM = a 2xx with a message name (success body NOT SOURCEABLE, F205). Neither means delivered (F202, F210). **Outcome map** for the job handler (`Retry`, `Dead`, plus a side effect on the subscription):

| Response | Outcome | Subscription/token |
|---|---|---|
| Web Push 201; FCM 2xx | done | `last_ok_at` updated |
| Web Push 429, FCM `QUOTA_EXCEEDED` 429 | Retry; honour `Retry-After` (F202); FCM message/topic limit initial delay at least 1 min (F207) | keep |
| FCM `UNAVAILABLE` 503, `INTERNAL` 500; Web Push 5xx (inference: RFC 8030 lists no 5xx) | Retry with backoff + jitter, `Retry-After` if present (F207) | keep |
| Web Push 404 (RFC: subscription expired, F202); 410 (not in RFC 8030 submission; used in practice, NOT SOURCEABLE here) | Dead(`recipient_gone`) | **delete the subscription** (treat 404 and 410 alike) |
| FCM `UNREGISTERED` 404 | Dead(`recipient_gone`) | **delete the token** (F207, F209) |
| FCM `INVALID_ARGUMENT` 400 | Dead(`rejected`) | delete only if our payload validated (F209); else keep and alert |
| Web Push 400, 413 | Dead(`rejected`): our bug (missing TTL, bad Topic, oversize) | keep; alert |
| Web Push 401/403 (VAPID, F204); FCM 403 `SENDER_ID_MISMATCH`, 401 | Dead(`credential`) + alert, open the breaker; one token refresh for an expired OAuth token first (Google error shape NOT SOURCEABLE, F220c) | keep |
| Timeout / connection error | Retry | keep |

5. **ADR-0012 amendment needed for push (F218):** the provider will not absorb a duplicate. ADR-0013 states at-least-once to the device with de-duplication by notice id at the client, and sets Web Push `Topic` from the item id (32 URL-safe characters, F201) to replace an outstanding duplicate.
6. **TTL and urgency:** set TTL to the request's remaining life (approval: at most 10 minutes, ASVS 6.5.5, F216); owner alerts: hours, not days (a late "till variance" alert is noise; value is a product choice); Web Push urgency `high` for approvals only (RFC 8030 names time-sensitive alerts, F201); FCM TTL 0 to 28 days (F210). FCM priority rules: NOT SOURCEABLE (F220b); F308 says use high priority against Doze.
7. **Subscription lifecycle (design from F203, F209, F216):** one row per (tenant, person, client install) holding kind, endpoint or token, the Web Push p256dh and auth secret (a secret: encrypted at rest), the VAPID key id used (F204 s4.2), created, last_ok_at. Created only from an authenticated dashboard session; deleted on 404/410/UNREGISTERED, on sign-out and on revoke (ASVS 6.5.6), on person erasure (ADR-0005), and by a recurring prune job: FCM tokens untouched for 30 days are suspect, 270 days expired (F209). Tokens/subscriptions are personal data tied to a person (privacy classification: `privacy-compliance-specialist`).
8. **Approval channel: R1.** The push says only "an approval is waiting" with the request id; the owner opens the dashboard, which loads details under RLS, and approves with step-up bound to the request (ADR-0007 s7 pattern; ASVS 6.6.2). No approval from the push itself (R2 rejected), no email channel (R3 rejected; email only as a notice). The approval returns to the counter by the sync nudge or a poll of 2 s or less (F217).
9. **Can remote approval sit on a counter path? No.** It waits on a person and a network the counter does not control, and push has no latency guarantee in any source read (F201 gives TTL and urgency, no time; F220g). The counter's own action ("ask for approval") must complete locally under the 3 s ceiling and show a waiting state; the sale proceeds or is cancelled by the cashier, and the local manager-PIN override of ADR-0007 stays the in-line path. The approval is an asynchronous workflow with its own lifetime. The only latency the counter owns is the poll/nudge that picks the answer up (ADR-0007: 2 s or less; dashboard-to-counter p95 <= 5 s proposed, not measured, F217).
10. **Fallbacks when push is late, lost or stale:** the request stays in the dashboard's pending list (badge, refreshed by polling while open; the mechanism is a design choice for the spec); a stale subscription is deleted on the first 404/410/UNREGISTERED and the request is re-offered by email notice to the owner (ids only, link to sign-in) once the push item ends Dead; the request expires at its lifetime and the counter is told by the same poll.

**Why the others lost:** B alone drags in Google services and a Play-listed wrap for everything and leaves the browser dashboard without push; A alone is the riskiest on a phone until S32, so the FCM adapter stays a prepared option; D misses the founder's alert need. R2 and R3 fail the security rows (F216).
**ADR needed:** yes, ADR-0013 (it also amends the ADR-0001 s1c `auth_notices` claim/ack list per ADR-0012).
**Proposed pin changes:** none now. Candidates once chosen: `nl.martijndwars:web-push` 5.1.2 or `com.google.firebase:firebase-admin` 9.11.0, `bcprov-jdk18on` 1.86, `google-auth-library-oauth2-http` 1.54.0 (F211, F212); `pins.yaml` is edited by the user, not by this note.

### 7. Performance & Caching Notes

- **Expected load:** low. Owner alerts and approval nudges are per tenant, a handful per day to some hundreds in a busy venue; no figure is sourced (this is an estimate, to be set by the spec). Payload at most 3993 bytes plaintext on Web Push, 4096 bytes on FCM (F203, F208); we send tens of bytes.
- **Hot paths:** none on the counter. The approval path is: counter request (local, under 3 s) -> sync -> backend creates the request and enqueues a push item -> push provider -> owner opens dashboard -> approve -> counter picks it up by nudge or poll <= 2 s (F217). Push latency is not on any budget; the budgets touched are `perf-budgets.md` "dashboard change reaches an online counter p95 <= 5 s" (proposed, unmeasured) and the 3 s counter ceiling (not applicable to the human wait, section 5 item 9).
- **Job-runner fit:** one push per item per transaction (ADR-0012 Decision 3), provider call outside the transaction under a timeout and breaker; `leaseDuration` must exceed timeout plus retry budget. Use a circuit breaker per destination kind (one for FCM, one per Web Push service host) so one slow push service does not stall the others.
- **Caching candidates (gate 5, decision goes in the spec/`cache-design.md`):** (a) the FCM OAuth access token: in-process, single-flight refresh, TTL taken from the token's own expiry (lifetime NOT SOURCEABLE, F206); not shared across instances; (b) the parsed VAPID key pair, loaded once at start; (c) **no cache** for subscriptions: read per send from the table under RLS (low volume, must reflect deletion at once). Key schema, invalidation and stampede protection for (a): single-flight, written in the cache design.
- **Budgets to add:** a push-adapter timeout and retry budget (config, not hard-coded); prune job cost; subscription table size per tenant.
